# 리렌더링과 렌더링 아키텍처(SPA/MPA, CSR/SSR) 이해하기

*"왜 이 컴포넌트가 다시 그려지지?"라는 질문과 "SPA가 SSR이 될 수도 있나?"라는 질문은 사실 같은 뿌리에서 나옵니다. 둘 다 "화면이 언제, 어디서, 어떻게 다시 계산되는가"에 대한 질문이기 때문입니다.*

## 1. 리렌더링이란 무엇인가

**리렌더링**(re-render)은 상태나 props가 변경되었을 때 프레임워크가 컴포넌트를 다시 실행해서 화면에 반영할 새로운 결과물을 계산하는 과정입니다. React는 리렌더링이 일어난다고 매번 실제 DOM을 통째로 다시 그리지 않습니다. 새로운 Virtual DOM 트리를 만들고, 이전 트리와 비교(diffing)해서 달라진 부분만 실제 DOM에 반영합니다.

React 공식 문서가 설명하는 화면 업데이트 3단계는 다음과 같습니다.

1. **Trigger** — 렌더링을 유발
2. **Render** — 컴포넌트 함수 호출·결과 계산
3. **Commit** — 실제 DOM에 반영 (눈에 보이는 단계)

> **공식 문서 · React** — "Render"는 곧 "React가 여러분의 컴포넌트 함수를 호출하는 것"을 의미할 뿐, 화면에 뭔가 그려지는 단계가 아닙니다. 실제로 눈에 보이는 변화는 마지막 **Commit** 단계에서만 일어납니다.

## 2. 리렌더링이 발생하는 조건

- 컴포넌트 자신의 state가 변경될 때
- 부모로부터 받은 props가 변경될 때
- 부모 컴포넌트가 리렌더링되어 자식도 함께 재실행될 때 — React는 기본적으로 부모가 리렌더링되면 자식도 리렌더링합니다
- 구독 중인 Context 값이 변경될 때

불필요한 리렌더링을 줄이기 위해 `React.memo`, `useMemo`, `useCallback` 같은 최적화 도구를 씁니다. 이 도구들은 "리렌더링 자체를 막는 것"이 아니라 "얕은 비교(shallow comparison) 결과가 같으면 리렌더링을 건너뛰게 하는 것"입니다.

> **공식 문서 · React** — 이런 최적화는 트리 상위에서 발생한 업데이트가 성능 문제가 될 때 선택적으로 적용할 수단이며, "성급하게 최적화하지 말라(Don't optimize prematurely)"고 안내합니다. 또한 렌더링은 항상 순수한 계산이어야 합니다 — 같은 입력(state, props)이면 항상 같은 JSX를 반환해야 하고, 렌더링 이전부터 존재하던 객체나 변수를 변경해서는 안 됩니다.

## 3. SPA vs MPA

**MPA**(Multi Page Application)는 페이지를 이동할 때마다 서버에 새 HTML을 요청하고, 브라우저가 페이지를 처음부터 다시 로드합니다. **SPA**(Single Page Application)는 최초에 하나의 HTML을 로드한 뒤, 이후 페이지 전환은 자바스크립트가 필요한 부분만 갈아끼웁니다.

| | MPA — 전체 새로고침 | SPA — 부분 갱신 |
| --- | --- | --- |
| ① | 링크 클릭 | 링크 클릭 |
| ② | 서버에 새 HTML 요청 | 라우터가 필요한 부분만 계산 |
| ③ | 페이지 전체 다시 로드 | 해당 영역만 DOM 교체 |
| ④ | 화면 깜빡임 발생 | 새로고침 없이 즉시 전환 |

| 구분 | MPA | SPA |
| --- | --- | --- |
| 페이지 전환 | 전체 새로고침 | 부분 갱신(라우팅) |
| 초기 로딩 | 상대적으로 빠름 | JS 번들 다운로드로 느릴 수 있음 |
| 전환 속도 | 느림(서버 왕복) | 빠름(클라이언트 처리) |
| SEO | 유리(완성된 HTML) | 기본적으로 불리 |
| 서버 부하 | 매 요청마다 렌더링 | 최초 1회 + API 위주 |

## 4. CSR vs SSR, 그리고 SSG

**CSR**은 서버가 빈 HTML과 JS 번들만 내려주고 브라우저가 화면을 그립니다. **SSR**은 서버에서 미리 HTML을 완성해서 내려줍니다. 이후 JS가 로드되어 이벤트 핸들러를 붙이는 과정을 **하이드레이션**(Hydration)이라고 부릅니다. **SSG**는 빌드 시점에 미리 HTML을 만들어둡니다.

*web.dev 기준 체감 로딩 흐름 비교 (예시, 실제 수치 아님) — FCP는 콘텐츠가 처음 보이는 시점, Interactive는 실제로 클릭 등에 반응 가능한 시점입니다.*

| 방식 | FCP (첫 콘텐츠) | Interactive (반응 가능) |
| --- | --- | --- |
| CSR | 느림 | 더 늦음 |
| SSR | 빠름 | CSR보다는 빠르지만 여전히 지연 |
| SSG | 매우 빠름 | 거의 즉시 |

> **공식 문서 · web.dev** — 하이드레이션은 "서버에서 렌더링된 HTML에 애플리케이션 상태와 상호작용성을 더하기 위해 클라이언트 스크립트를 실행하는 것"입니다. SSR·SSG 모두 화면은 보이는데 클릭에 반응하지 않는 구간이 길어지면 응답성 지표(INP)가 나빠질 수 있는데, web.dev는 이를 **"한 앱을 두 번 만드는 문제(one app for the price of two)"** 라 부릅니다. 서버가 렌더링한 HTML과 별개로, 클라이언트가 같은 UI를 다시 만들기 위한 JS 번들과 데이터를 통째로 다시 받고 실행해야 하기 때문입니다. 이를 완화하려고 스트리밍 SSR, 점진적 하이드레이션(progressive hydration) 같은 기법이 쓰입니다.

| 구분 | CSR | SSR | SSG |
| --- | --- | --- | --- |
| HTML 생성 시점 | 브라우저에서 | 매 요청 시 서버 | 빌드 시점에 미리 |
| 초기 콘텐츠 속도 | 느림 | 빠름 | 매우 빠름 |
| SEO | 불리 | 유리 | 유리 |
| 서버 부하 | 낮음 | 요청마다 발생 | 거의 없음 |
| 대표 프레임워크 | CRA, Vite | Next.js, Nuxt | Next.js(SSG), Astro |

## 5. 두 축은 독립적이다

SPA/MPA와 CSR/SSR은 서로 다른 축입니다. SPA라고 해서 반드시 CSR만 쓰는 것은 아니고, Next.js처럼 SPA의 부드러운 전환을 유지하면서도 최초 로딩이나 특정 페이지만 SSR/SSG로 렌더링하는 하이브리드 구조가 오늘날 표준에 가깝습니다.

## 마무리

리렌더링은 컴포넌트 레벨에서 "언제 다시 계산할 것인가"의 문제이고, SPA/MPA·CSR/SSR은 애플리케이션 레벨에서 "화면을 어디서, 어떤 방식으로 처음 그리고 전환할 것인가"의 문제입니다. 규모가 작고 SEO가 중요하지 않다면 CSR 기반 SPA로 충분하지만, 초기 로딩 속도와 검색 노출이 중요하다면 SSR·SSG를 섞은 하이브리드 구조를 고려하는 것이 합리적입니다.
