# 프론트엔드 상태관리, 제대로 이해하기

*프론트엔드 개발에서 가장 자주 등장하는 단어 중 하나가 "상태관리(State Management)"입니다. Redux, Zustand, Recoil, Pinia 같은 이름은 한 번쯤 들어봤겠지만, 정작 "상태가 뭔지", "왜 관리가 필요한지"부터 짚고 넘어가면 이후 도구 선택이 훨씬 수월해집니다.*

## 1. 상태(State)란 무엇인가

상태는 "시간이 지나면서 변할 수 있고, 그 변화가 화면에 반영되어야 하는 데이터"입니다. 사용자가 입력한 텍스트, 서버에서 받아온 목록, 모달의 열림/닫힘 여부 같은 것들이 모두 상태입니다.

중요한 건 상태와 "그냥 변수"의 차이입니다. 단순 변수는 값이 바뀌어도 화면이 저절로 갱신되지 않지만, 상태는 값이 바뀌면 프레임워크가 이를 감지해 화면을 다시 그립니다.

> **공식 문서 · React** — 상태는 두 가지 요건으로 설명됩니다. 렌더링 사이에 데이터를 **유지**(retain)해야 하고, 새 데이터로 컴포넌트를 다시 그리도록 React를 **트리거**(trigger)해야 합니다. `useState`가 반환하는 상태 변수와 setter 함수가 각각 이 두 역할을 맡습니다. 또한 "State is isolated and private" — 같은 컴포넌트를 두 번 렌더링해도 각 인스턴스는 완전히 독립된 상태를 가지며, 부모조차 자식의 상태를 직접 바꿀 수 없습니다.

## 2. 상태의 세 가지 종류

상태는 크게 세 가지로 나눌 수 있습니다.

| 종류 | 설명 |
| --- | --- |
| 로컬 상태 | 특정 컴포넌트 안에서만 쓰임. 입력창 값, 아코디언 열림 여부 등. |
| 전역 상태 | 여러 컴포넌트가 공유. 로그인 정보, 다크모드, 장바구니 등. |
| 서버 상태 | 진짜 소스는 서버. 클라이언트는 요청·캐싱만. 게시글 목록 등. |

**로컬 상태**(Local State)는 특정 컴포넌트 안에서만 쓰이는 상태입니다. **전역 상태**(Global State)는 여러 컴포넌트가 공유해야 하는 상태입니다. **서버 상태**(Server State)는 진짜 소스가 서버에 있고, 클라이언트는 이를 요청해서 캐싱한 뒤 보여줄 뿐인 상태입니다. TanStack Query(구 React Query)나 SWR 같은 라이브러리가 이 영역을 전담합니다.

> **공식 문서 · TanStack Query** — 서버 상태가 클라이언트 상태와 다른 이유는 명확합니다.
>
> - 내가 통제할 수 없는 원격 위치에 저장됨
> - 조회·갱신에 비동기 API가 필요함
> - 다른 사람이 내 모르게 데이터를 바꿀 수 있어 소유권이 공유됨
> - 시간이 지나면 "오래된" 상태가 될 수 있음
>
> 그래서 캐싱, 중복 요청 제거, 백그라운드 최신화 같은 문제를 별도로 풀어야 하며, 이것이 전용 라이브러리가 필요한 이유입니다.

이 세 가지를 구분하지 않고 전부 하나의 전역 스토어에 몰아넣으면 관리가 복잡해집니다. 최근 흐름은 "서버 상태는 서버 상태 전용 도구로, UI용 로컬/전역 상태는 별도로" 분리하는 방향입니다.

## 3. 상태관리가 어려워지는 이유: Prop Drilling

컴포넌트 트리가 깊어질수록 상위 컴포넌트의 상태를 하위 컴포넌트까지 전달해야 하는 상황이 생깁니다. 이를 여러 단계에 걸쳐 props로 넘기는 것을 **prop drilling**이라고 부릅니다.

```jsx
function App() {
  const [user, setUser] = useState(null);
  return <Layout user={user} />;
}
function Layout({ user }) {
  return <Header user={user} />;
}
function Header({ user }) {
  return <Profile user={user} />;
}
```

이 예시를 트리로 그려보면 이렇습니다.

| 컴포넌트 | 역할 |
| --- | --- |
| `App` | `user` 상태를 생성 |
| `Layout` | `user`를 props로 받기만 함 (전달만, 사용 안 함) |
| `Header` | `user`를 props로 받기만 함 (전달만, 사용 안 함) |
| `Profile` | `user`를 실제로 사용 |

우회 경로: Context나 전역 스토어를 쓰면 `Layout`·`Header`를 거치지 않고 `App`에서 `Profile`로 직접 상태를 전달할 수 있습니다.

`Layout`과 `Header`는 `user`를 실제로 쓰지 않는데도 단순히 전달만 하기 위해 props를 받아야 합니다. 해결 방법은 두 가지입니다. **상태를 실제로 필요한 위치까지만 끌어올리는 것**(state lifting)이거나, **Context API나 전역 상태관리 라이브러리로 트리를 우회해서 필요한 컴포넌트에 직접 상태를 전달하는 것**입니다.

## 4. 상태관리 라이브러리 비교

- **React**: Redux, Zustand, Jotai, Recoil
- **Vue**: Vuex, Pinia

> **공식 문서 · Redux — Three Principles**
>
> - **Single source of truth** — 전역 상태는 하나의 스토어 안 단일 객체 트리로 저장
> - **State is read-only** — 상태는 읽기 전용이며, "무슨 일이 일어났는지"를 설명하는 액션(action)을 통해서만 변경 의도를 표현
> - **Changes with pure functions** — 상태 변화는 순수 함수인 리듀서(reducer)로 작성, 이전 상태를 직접 변경하지 않고 항상 새 객체를 반환

이 원칙 덕분에 상태 변화가 예측 가능해지지만, 보일러플레이트가 많다는 비판을 받아왔고 이를 줄이기 위해 등장한 것이 Redux Toolkit입니다. **Zustand**와 **Jotai**는 훨씬 가벼운 API로 전역 상태를 다룰 수 있게 해줍니다. Zustand는 스토어를 훅처럼 만들어 쓰는 방식이라 러닝커브가 낮고, Jotai는 상태를 작은 단위(atom)로 쪼개 관리해 불필요한 리렌더링을 줄이기 좋습니다. **Recoil**도 atom 기반이지만 메타에서 개발이 사실상 정체된 상태입니다.

> **공식 문서 · Pinia vs Vuex** — 장황하다는 평을 받던 mutation 개념이 사라졌고, 복잡한 래퍼 없이도 타입스크립트 추론이 자연스럽게 동작하며, 네임스페이스 중첩 구조 대신 평평한(flat) 구조로 스토어를 정의합니다. 데브툴 연동으로 액션 타임라인 추적·타임 트래블 디버깅을 지원하고, 새로고침 없이 스토어 코드를 수정할 수 있는 HMR도 제공합니다.

## 5. 결국 핵심은 "누가 리렌더링되는가"

이 도구들이 공통적으로 하는 일은 "컴포넌트 트리 바깥에 상태를 두고, 그 상태를 구독(subscribe)한 컴포넌트만 값이 바뀔 때 리렌더링되게 만드는 것"입니다. 전역 상태를 하나의 거대한 객체로 관리하면 관련 없는 컴포넌트까지 리렌더링될 위험이 있고, atom 단위로 잘게 쪼개면 그만큼 불필요한 리렌더링을 줄일 수 있습니다.

## 마무리

상태관리는 결국 "어떤 데이터를 어디에 두고, 누가 그 데이터를 구독하게 할 것인가"를 설계하는 문제입니다. 작은 프로젝트에서는 로컬 상태와 Context API만으로도 충분하지만, 프로젝트가 커질수록 서버 상태와 클라이언트 상태를 분리하고, 전역 상태를 필요한 범위로 쪼개는 설계가 중요해집니다.
