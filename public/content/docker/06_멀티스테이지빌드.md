# [Docker 개념 6편] 880MB 이미지를 428MB로 줄이는 방법, 멀티스테이지 빌드

전통적인 빌드 방식에서는 의존성 다운로드, 코드 컴파일, 패키징까지 모든 과정이 하나의 빌드 컨테이너 안에서, 순서대로 실행됩니다. 문제는 이 모든 레이어가 최종 이미지에 그대로 남는다는 점입니다. 컴파일러, 빌드 도구, 중간 산출물까지 전부 프로덕션 이미지에 딸려가면서 이미지가 불필요하게 무거워지고, 공격 표면(attack surface)도 함께 늘어납니다. 이 문제를 푸는 방법이 멀티스테이지 빌드입니다.

## 멀티스테이지 빌드란

Dockerfile 안에 여러 개의 스테이지를 두고, 각 스테이지가 서로 다른 목적을 갖도록 만드는 방식입니다. 빌드 환경과 최종 실행 환경을 분리함으로써 이미지 크기와 공격 표면을 크게 줄일 수 있습니다. 공식 문서는 모든 종류의 애플리케이션에 멀티스테이지 빌드를 권장합니다.

- JavaScript, Ruby, Python 같은 인터프리터 언어라면, 한 스테이지에서 코드를 빌드·압축(minify)하고, 그 결과물만 더 작은 런타임 이미지로 복사합니다.
- C, Go, Rust 같은 컴파일 언어라면, 한 스테이지에서 컴파일하고 컴파일된 바이너리만 최종 이미지로 복사합니다. 컴파일러 전체를 최종 이미지에 담을 필요가 없습니다.

의사 코드로 표현하면 이런 구조입니다.

```dockerfile
# 스테이지 1: 빌드 환경
FROM builder-image AS build-stage
# 빌드 도구 설치, 소스 복사, 빌드 명령 실행

# 스테이지 2: 런타임 환경
FROM runtime-image AS final-stage
# 빌드 스테이지에서 결과물만 복사
COPY --from=build-stage /path/in/build/stage /path/to/place/in/final/stage
# CMD, ENTRYPOINT 등 런타임 설정
```

## 실제 예시: Spring Boot 애플리케이션

공식 문서의 실습 예시를 보면 차이가 확실히 드러납니다. 멀티스테이지가 아닌 기본 빌드는 다음과 같습니다.

```dockerfile
FROM eclipse-temurin:21.0.8_9-jdk-jammy
WORKDIR /app
COPY .mvn/ .mvn
COPY mvnw pom.xml ./
RUN ./mvnw dependency:go-offline
COPY src ./src
CMD ["./mvnw", "spring-boot:run"]
```

이 이미지는 JDK와 Maven 툴체인을 전부 포함해 크기가 880MB에 달합니다. 이걸 멀티스테이지로 바꾸면 다음과 같습니다.

```dockerfile
FROM eclipse-temurin:21.0.8_9-jdk-jammy AS builder
WORKDIR /opt/app
COPY .mvn/ .mvn
COPY mvnw pom.xml ./
RUN ./mvnw dependency:go-offline
COPY ./src ./src
RUN ./mvnw clean install

FROM eclipse-temurin:21.0.8_9-jre-jammy AS final
WORKDIR /opt/app
EXPOSE 8080
COPY --from=builder /opt/app/target/*.jar /opt/app/*.jar
ENTRYPOINT ["java", "-jar", "/opt/app/*.jar"]
```

첫 번째 스테이지(`builder`)는 컴파일에 필요한 JDK 환경을 그대로 쓰고, 두 번째 스테이지(`final`)는 실행에만 필요한 가벼운 JRE 이미지를 베이스로 삼아 빌드 결과물(.jar 파일)만 복사해옵니다. 결과적으로 이미지 크기는 428MB로, 원래의 절반 이하로 줄어듭니다.

## 조금 더 깊이: 기본 빌드 대상은 마지막 스테이지

멀티스테이지 Dockerfile에서 `docker build` 명령에 `--target` 플래그를 따로 지정하지 않으면, Docker는 자동으로 마지막 스테이지(위 예시에서는 `final`)를 빌드합니다. 디버깅을 위해 중간 단계인 `builder` 스테이지까지만 빌드하고 싶다면 `docker build --target builder .`처럼 명시적으로 지정하면 됩니다. 이 기능은 개발 중에는 도구가 포함된 빌드 이미지를 쓰고, 배포할 때는 최종 이미지만 만드는 식으로 유연하게 활용할 수 있습니다.

또한 JRE 대신 `jlink`로 애플리케이션에 필요한 모듈만 담은 커스텀 런타임을 만들면 이미지를 한층 더 작고 안전하게 만들 수 있습니다. Eclipse Temurin 이미지는 이런 커스텀 런타임 구성을 지원합니다.

## 참고표

| 방식 | 최종 이미지에 남는 것 | 이미지 크기 경향 |
|---|---|---|
| 단일 스테이지 빌드 | 빌드 도구 + 실행에 필요한 것 전부 | 큼 |
| 멀티스테이지 빌드 | 실행에 필요한 결과물만 | 작음 |
