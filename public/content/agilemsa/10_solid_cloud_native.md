# 모놀리식에서 MSA로: SOLID 원칙과 단계적 전환 전략

*기존 시스템을 하루아침에 MSA로 바꾸는 팀은 거의 없습니다. 시리즈 마지막 편에서는 코드 레벨의 리팩토링 원칙인 SOLID와, 인프라 레벨의 단계적 클라우드 전환 전략을 함께 살펴보며 지금까지의 내용을 마무리합니다.*

## 코드 레벨: 뒤엉킨 책임을 먼저 풀어낸다

MSA로 옮기기 전에, 기존 코드 안에서 여러 책임이 뒤엉켜 있는 경우가 많습니다. 예를 들어 로그인 기능 하나가 입력 검증, 비밀번호 확인, 세션 생성, 로그 기록을 모두 한 클래스에서 처리하고 있다면, 이 로직만 따로 떼어 다른 서비스로 옮기는 것 자체가 매우 어렵습니다.

Before — 뒤엉킨 단일 클래스
      
        하나의 클래스가 입력 검증, 비밀번호 확인, 세션 생성, 로그 기록을 모두 담당
        인증 로직만 따로 떼어 재사용하거나 다른 서비스로 옮기기 어려움
        테스트 시 전체 클래스를 실행해야 하며, 일부 로직만 검증하기 힘듦
      
    
    After — SOLID 적용 후 구조
      
        검증·세션 관리·로그 기록이 각각 별도 클래스로 책임 분리
        인증 방식(비밀번호/OAuth)이 추가돼도 기존 코드 수정 없이 확장
        인터페이스에 의존하므로 구현체를 자유롭게 교체 가능

이렇게 책임을 분리해두면, 나중에 이 컴포넌트들을 그대로 독립된 마이크로서비스(예: 인증서버)로 옮기는 작업이 훨씬 수월해집니다. SOLID는 사실 MSA 전용 원칙이 아니라 오래된 객체지향 설계 원칙이지만, MSA 전환의 첫 단계로 특히 자주 언급됩니다.

    <tbody><tr><th>약자</th><th>원칙</th><th>핵심 내용</th></tr>

> 세 단계는 절대적인 기준이 아닙니다. 애플리케이션을 클라우드에 최적화된 형태로 한번에 전환하기는 어렵기 때문에, 기존 시스템 특성에 맞춰 **단계적으로 진화** 시켜 나간다는 것을 보여주기 위한 구분입니다. 어떤 시스템은 Cloud Ready 단계만으로 충분한 효과를 볼 수도 있고, 어떤 시스템은 처음부터 Cloud Native까지 밀어붙여야 할 수도 있습니다.

## 참고할 만한 체크리스트: 12 Factor App

클라우드 애플리케이션을 설계할 때 참고하는 대표적인 표준 원칙이 "12 Factor App"입니다. 코드와 설정을 분리하고, 서비스 간 통신을 네트워크 기반으로 간주하고, 무상태(Stateless) 처리를 기본으로 하며, 배포 환경 간 차이를 최소화하는 등 12가지 항목으로 구성됩니다. 이 원칙들을 PaaS(플랫폼 as a 서비스) 환경과 DevOps 파이프라인만으로 상당 부분 달성할 수 있고, 나머지는 코드 리팩토링으로 채워야 합니다. 처음부터 전체 애플리케이션에 무리하게 적용하려 하지 말고, 영향이 적은 서비스 하나부터 검증하며 넓혀가는 태도가 중요합니다.

#### 핵심 키워드

- **SOLID**: 객체지향 설계의 다섯 가지 원칙(SRP, OCP, LSP, ISP, DIP)을 묶어 부르는 이름. 코드의 유연성과 재사용성을 높인다.
- **리팩토링 (Refactoring)**: 겉으로 보이는 동작은 바꾸지 않으면서, 내부 코드 구조를 더 나은 형태로 개선하는 작업.
- **Cloud Native**: 클라우드 환경의 특성(탄력적 확장, 장애 복원력 등)을 최대한 활용하도록 처음부터 설계된 애플리케이션 방식.
- **12 Factor App**: 클라우드 애플리케이션을 구축하기 위한 12가지 표준 설계 원칙 모음.
- **PaaS (Platform as a Service)**: 인프라와 서비스 아키텍처 관리를 제공받고, 개발팀은 애플리케이션 코드에만 집중할 수 있게 해주는 클라우드 서비스 형태.

시리즈를 마치며 — 애자일과 MSA는 결국 같은 문제의식에서 출발합니다. "변화는 항상 일어난다. 그렇다면 변화에 빨리, 안전하게 대응할 수 있는 방식으로 일하고, 그런 구조로 시스템을 만들자"는 것입니다. 도구나 용어를 외우기보다, 이 문제의식을 팀이 함께 공유하는 것이 실제 도입의 출발점입니다.
