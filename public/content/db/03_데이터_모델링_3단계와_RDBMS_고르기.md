# ERD부터 DBMS 선택까지 — 설계는 세 단계로 나눠서 하자

"일단 테이블부터 만들고 시작하자"는 말, 소규모 프로젝트에서는 통한다. 하지만 팀 프로젝트나 실서비스에서 이렇게 시작하면 몇 주 뒤 반드시 후회한다. 요구사항이 바뀔 때마다 테이블을 뒤엎어야 하기 때문이다. 오늘은 설계를 안전하게 나눠서 진행하는 3단계 방법과, 그렇게 설계한 걸 어떤 DBMS에 얹을지 고르는 기준을 정리한다.

## 개념 설계 → 논리 설계 → 물리 설계

실제로 DB를 만들 때는 세 단계를 거치는 게 안전하다.

**1. 개념적 모델링**: 특정 DBMS를 신경 쓰지 않고 비즈니스 요구사항을 추상화하는 단계다. 요구사항 문서에서 명사를 뽑아 엔티티를 정의하고(학생, 강의, 교수), 엔티티 사이의 관계를 정의해 ERD(개체-관계 다이어그램)를 그린다.

**2. 논리적 모델링**: 개념 모델을 실제 테이블 구조로 옮기는 단계다. 기본키·외래키를 정하고 정규화를 적용한다. (지난 편에서 다룬 내용이 바로 여기서 쓰인다.)

**3. 물리적 모델링**: 특정 DBMS 환경에 맞춰 데이터 타입, 인덱스, 파티셔닝 전략까지 구체화하는 단계다. 예를 들어 금액은 부동소수점 오차를 피하려고 `NUMERIC`으로, 시간은 글로벌 서비스를 고려해 시간대 정보를 포함한 `TIMESTAMPTZ`로 정하는 식이다.

ERD를 그릴 때는 관계의 종류(하나/여럿/없거나 하나 등)를 표시하는 IE 표기법(일명 까마귀발 표기법)을 많이 쓴다. 여기서 한 가지 챙겨둘 개념이 **약한 엔티티** 다. 독자적인 기본키 없이 다른 강한 엔티티(부모)에 의존해서만 식별되는 엔티티인데, "주문 없이는 존재할 수 없는 주문 상세" 같은 게 대표적이다. ERD에서는 이중 사각형으로 표시하고, 부모가 삭제되면 함께 삭제되도록(`ON DELETE CASCADE`) 설계하는 게 일반적이다.

```sql
-- 약한 엔티티: order_items는 orders 없이 존재 불가
CREATE TABLE order_items (
  order_id INT REFERENCES orders(id) ON DELETE CASCADE,
  item_no SMALLINT NOT NULL,
  product_id INT REFERENCES products(id),
  quantity INT NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (order_id, item_no)  -- 복합 PK
);
```

## 어떤 RDBMS를 골라야 할까

설계가 끝나면 이제 어느 DBMS 위에 올릴지 결정해야 한다. 실무에서 자주 쓰이는 관계형 데이터베이스는 저마다 강점이 다르다.

| DBMS | 특징 | 주로 쓰이는 곳 |
|---|---|---|
| MySQL / MariaDB | 가볍고 빠르며 배우기 쉬움, InnoDB 기준 트랜잭션·MVCC 지원 | 웹 서비스, 스타트업 |
| PostgreSQL | 오픈소스 중 가장 표준 SQL에 충실, JSONB·GIS·벡터 검색 등 확장 풍부 | 데이터 분석, 금융, AI 서비스 |
| Oracle | 강력한 안정성과 고급 기능(RAC, Data Guard) | 은행, 대기업 ERP |
| SQL Server | 마이크로소프트 생태계(Windows, PowerBI)와 밀접히 통합 | 사내 ERP·CRM, BI 리포팅 |
| 클라우드 DB(AWS Aurora, GCP Cloud SQL 등) | 백업·장애복구를 관리형 서비스가 대신 처리 | 글로벌 서비스, 빠른 확장이 필요한 조직 |

신규 프로젝트에서 고민된다면, 개인적으로는 PostgreSQL을 먼저 검토해보길 권한다. 표준 SQL을 충실히 따르면서도 JSON·벡터 검색 같은 최신 요구사항까지 확장 기능으로 커버하기 때문에, 나중에 요구사항이 바뀌어도 유연하게 대응할 수 있다.

## 왜 어느 DB에서든 SQL이 통할까

MySQL에서 짠 `SELECT`가 PostgreSQL에서도 대체로 통하는 이유는 국제 표준이 있기 때문이다. 1986년 미국표준협회(ANSI)가 처음 SQL을 표준화했고, 이후 국제표준화기구(ISO)와 함께 관리하며 주기적으로 개정해왔다. 가장 최근 판은 2023년 6월 확정된 ISO/IEC 9075:2023(SQL:2023)으로, JSON 관련 기능이 확장되고 SQL 위에 그래프 질의 언어를 얹은 SQL/PGQ가 새로 추가됐다.

다만 실무에서는 벤더별로 세부 문법이 조금씩 다르다는 걸 감안해야 한다. 상위 몇 건만 조회할 때 MySQL은 `LIMIT`, SQL Server는 `TOP`을 쓰는 식이다. 여러 DB를 넘나드는 프로젝트라면 되도록 `COALESCE()`, `FETCH FIRST n ROWS ONLY` 같은 표준 문법으로 작성해 이식성을 확보하고, 성능 튜닝처럼 꼭 필요할 때만 DB 전용 문법을 쓰는 전략이 낫다.

**오늘의 한 줄 요약**: 설계는 개념 → 논리 → 물리 순서로 단계를 나눠야 나중에 덜 고생한다. 다음 편부터는 본격적으로 SQL 코드를 다룬다. 먼저 테이블을 만들고 데이터를 채우는 DDL·DML 기초부터 시작한다.
