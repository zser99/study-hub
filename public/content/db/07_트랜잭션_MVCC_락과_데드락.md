# 두 사람이 동시에 같은 재고를 깎으면 무슨 일이 생길까 — MVCC와 락

동시 접속자가 적을 땐 잘 몰랐던 문제가, 트래픽이 늘면서 갑자기 터진다. 같은 상품 재고를 두 사람이 동시에 주문했는데 재고가 마이너스로 떨어진다거나, 특정 시간대에 쿼리들이 서로 물려서 멈춰버리는 현상이다. 1편에서 격리 수준을 예고했었는데, 이번 편에서 그 실체와 락·데드락까지 실무 기준으로 정리한다.

## MVCC: 읽기와 쓰기가 서로 기다리지 않게

여러 사용자가 동시에 데이터를 읽고 쓸 때, 데이터를 곧바로 덮어쓰는 대신 새 버전을 만들어 저장하는 방식을 MVCC(Multi-Version Concurrency Control)라고 한다. PostgreSQL과 MySQL(InnoDB)을 비롯한 대부분의 현대 DB가 이 방식을 쓴다. 각 트랜잭션은 자신이 시작된 시점의 스냅샷을 보기 때문에, 읽기 작업이 쓰기 작업을 막지 않고 그 반대도 마찬가지다.

다만 공짜는 아니다. 더는 필요 없어진 예전 버전 데이터(Dead Tuple)가 계속 쌓이기 때문에, PostgreSQL은 `VACUUM`이라는 청소 작업으로 이를 주기적으로 회수해야 한다. 트랜잭션을 오래 열어두면 이 청소가 막혀서 테이블이 비대해지는(Table Bloat) 원인이 되니, "트랜잭션은 짧게"가 여기서도 원칙이다.

## 격리 수준, 상황에 맞게 고르기

1편에서 예고했던 더티 리드, 반복 불가능 읽기, 팬텀 리드는 격리 수준에 따라 허용 여부가 달라진다.

| 격리 수준 | 더티 리드 | 반복 불가능 읽기 | 팬텀 리드 |
|---|---|---|---|
| Read Uncommitted | 허용 | 허용 | 허용 |
| Read Committed | 방지 | 허용 | 허용 |
| Repeatable Read | 방지 | 방지 | 허용(표준상) |
| Serializable | 방지 | 방지 | 방지 |

실무에서는 작업 성격에 따라 다르게 고르는 게 좋다.

- 단순 조회는 최신 데이터를 빠르게 보여주는 **Read Committed** 로 충분하다. PostgreSQL·Oracle의 기본값이다.
- 반복 조회가 필요한 보고서는 같은 트랜잭션 안에서 일관된 값을 보장하는 **Repeatable Read** 가 적합하다. MySQL(InnoDB)의 기본값이다.
- 계좌 이체나 좌석 예매처럼 무결성이 절대적인 작업엔 가장 엄격한 **Serializable** 을 쓰되, 충돌 시 트랜잭션이 강제로 실패할 수 있으니 애플리케이션에서 재시도 로직을 준비해야 한다.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
UPDATE bank SET balance = balance - 100 WHERE name = 'Alice';
-- 동시에 다른 트랜잭션이 같은 행을 건드리면
-- ERROR: could not serialize access due to concurrent update
```

## 락(Lock)과 낙관적/비관적 전략

여러 트랜잭션이 같은 데이터를 동시에 바꾸려 하면 락이 필요하다. 두 가지 전략이 있다.

**낙관적 락** 은 충돌이 드물다고 가정하고, 저장 시점에 버전이 바뀌었는지만 확인한다. 읽기 위주 작업이나 블로그 댓글 수정처럼 충돌이 잦지 않은 곳에 적합하다.

```sql
UPDATE products SET stock = 10, version = version + 1
WHERE id = 1 AND version = 3;  -- 영향받은 행이 0이면 충돌 → 재시도
```

**비관적 락** 은 트랜잭션 시작과 동시에 행을 잠그고 다른 트랜잭션을 대기시킨다. 은행 이체나 재고 차감처럼 충돌이 잦고 반드시 순서를 지켜야 하는 작업에 적합하다.

```sql
BEGIN;
SELECT * FROM items WHERE id = 1 FOR UPDATE;  -- 이 행을 잠금
UPDATE items SET stock = stock - 1 WHERE id = 1;
COMMIT;  -- 여기서 잠금 해제
```

## 데드락, 왜 생기고 어떻게 줄일까

두 트랜잭션이 서로가 가진 자원을 기다리며 영원히 멈춰버리는 상황을 데드락(교착 상태)이라 한다.

```
세션 1: id=1 잠금 → id=2 요청 (대기)
세션 2: id=2 잠금 → id=1 요청 (대기)
→ 서로 기다리는 순환 발생!
```

대부분의 DB는 이를 자동으로 감지해 한쪽 트랜잭션을 강제로 취소시킨다. 하지만 애초에 데드락을 줄이려면 원칙이 있다. 여러 행을 잠글 때는 항상 같은 순서(예: ID 오름차순)로 잠그고, 트랜잭션은 가능한 한 짧게 유지하며, 트랜잭션 안에서 외부 API 호출처럼 오래 걸리는 작업을 하지 않는 것이다.

```sql
-- 항상 id 오름차순으로 잠가서 순환 대기를 방지
BEGIN;
SELECT id FROM items WHERE id = ANY(ARRAY[1,2]) ORDER BY id FOR UPDATE;
UPDATE items SET stock = stock - 1 WHERE id IN (1,2);
COMMIT;
```

**오늘의 한 줄 요약**: MVCC 덕분에 읽기와 쓰기는 서로를 막지 않지만, 쓰기끼리는 여전히 충돌할 수 있다. 작업 성격에 맞는 격리 수준을 고르고, 락은 항상 같은 순서로 걸자. 다음 편에서는 정규화를 넘어서는 고급 설계, 반정규화·샤딩과 스토어드 프로시저·트리거를 다룬다.
