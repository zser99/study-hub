# RDS냐 Aurora냐, 그리고 벡터 DB는 왜 갑자기 다들 쓰는 걸까

"DB는 그냥 RDS 켜면 되는 거 아니야?"라고 생각했다면 이번 편이 도움이 될 것이다. 클라우드 DB는 온프레미스와 뭐가 다르고, 요즘 화두인 벡터 DB는 실제로 뭘 하는 물건인지, 실무자 입장에서 알아야 할 만큼만 정리했다.

## 직접 운영할 것인가, 맡길 것인가

데이터베이스를 서버에 직접 설치하는 온프레미스는 자유도가 높은 대신 하드웨어 구매부터 패치, 백업까지 다 직접 책임져야 한다. 반면 AWS RDS, GCP Cloud SQL 같은 관리형 서비스(DBaaS)는 백업·장애 조치·모니터링을 대신 처리해준다. 다만 이게 스키마 설계나 쿼리 최적화 책임까지 사라진다는 뜻은 아니다. DBaaS는 "인프라"를 대신 관리해줄 뿐, "이 쿼리가 왜 느린지"는 여전히 우리 몫이다.

여기서 한 단계 더 나아간 게 Amazon Aurora나 Google Spanner 같은 클라우드 네이티브 DB다. 스토리지를 여러 곳에 자동 복제해 처음부터 분산과 고가용성을 염두에 두고 설계돼 있다. 실무에서 RDS와 Aurora를 고민한다면 이렇게 나눠보면 된다.

| 항목 | AWS RDS | Amazon Aurora |
|---|---|---|
| 구조 | 원본 엔진을 그대로 관리형으로 운영 | 컴퓨트·스토리지 분리, 자동 6중 복제 |
| 확장 | 읽기 복제본 수동 추가 | 리더 엔드포인트, 서버리스 v2 지원 |
| 선택 기준 | 엔진 호환성이 우선, 중소규모 | 읽기 부하가 크고 빠른 장애 조치가 필요할 때 |

무엇을 고를지는 데이터를 특정 국가 밖으로 반출할 수 없다는 규제가 있는지, DB를 직접 운영할 전문 인력이 있는지, 트래픽 변동이 큰지를 종합적으로 따져 결정하는 게 맞다.

## 트래픽에 맞춰 자동으로 늘고 줄어드는 DB

최근엔 사용한 만큼만 비용을 내고 트래픽이 없을 땐 자동으로 줄어드는 서버리스 DB도 늘고 있다. Aurora Serverless는 트래픽에 따라 자동으로 용량을 조절하고, Neon이나 PlanetScale처럼 사용하지 않을 때는 완전히 멈추는(scale-to-zero) 개발자 친화적 서비스도 주목받는다. 사이드 프로젝트나 초기 스타트업이라면 이런 서버리스 옵션으로 시작해 유휴 비용을 아끼는 것도 방법이다.

## 거래 처리용 DB와 분석용 DB는 다르다

우리가 흔히 쓰는 주문·결제 DB(OLTP)와, 그 데이터를 모아 매출 추이를 뽑는 분석 DB(OLAP, 데이터 웨어하우스)는 설계 방향이 근본적으로 다르다. OLTP는 짧고 잦은 단건 처리에, OLAP는 대량 데이터를 한 번에 훑어 집계하는 데 최적화돼 있다. 그래서 OLAP는 의도적으로 비정규화된 스타 스키마(중심에 거래 기록인 팩트 테이블을 두고, 상품·고객·시간 같은 디멘전 테이블이 둘러싸는 구조)를 쓰고, 데이터를 행이 아니라 컬럼 단위로 저장해 필요한 컬럼만 빠르게 읽는다. Google BigQuery, Amazon Redshift, Snowflake가 대표적이다. "우리 서비스 DB에 리포트 쿼리를 계속 날렸더니 느려졌다"는 문제는 십중팔구 OLTP용 DB에 OLAP성 쿼리를 섞어 쓴 게 원인이니, 분석이 잦아지면 별도 분석 DB를 분리하는 걸 검토하자.

## AI 시대, 벡터 DB는 왜 필요할까

최근 가장 많이 듣는 키워드가 벡터 DB일 것이다. 텍스트나 이미지를 숫자 벡터(임베딩)로 변환해 저장해두면, 의미가 비슷한 데이터를 빠르게 찾아낼 수 있다. PostgreSQL의 `pgvector` 확장처럼 기존 관계형 DB에 벡터 검색 기능을 더하는 방식도 있고, Pinecone처럼 벡터 검색 전용 서비스도 있다.

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE knowledge_base (
  id BIGSERIAL PRIMARY KEY,
  content TEXT,
  embedding VECTOR(1536)
);
CREATE INDEX ON knowledge_base USING HNSW (embedding vector_cosine_ops);

-- 질문 임베딩과 가장 유사한 문서 5개 검색
SELECT content FROM knowledge_base
ORDER BY embedding <=> '[0.01, 0.02, ...]'::VECTOR LIMIT 5;
```

이 기술은 요즘 화제인 RAG(검색 증강 생성), 즉 질문과 관련된 문서를 DB에서 찾아 언어모델에 함께 전달해 더 정확한 답변을 만드는 방식의 핵심 구성 요소다. 챗봇이나 사내 문서 검색 기능을 만들어본다면 이미 알고 있는 PostgreSQL에 `pgvector`만 얹어서 시작해볼 수 있다.

이 밖에도 관계형 DB의 트랜잭션 보장과 NoSQL의 수평 확장성을 동시에 노리는 NewSQL(CockroachDB, TiDB), 센서·로그처럼 시간 순으로 쌓이는 데이터에 특화된 시계열 DB(TimescaleDB)도 특정 용도에서 자리를 넓혀가고 있다. 요즘은 하나의 DB를 고집하기보다, 목적에 맞게 여러 DB를 섞어 쓰는 게 자연스러운 흐름이다.

**오늘의 한 줄 요약**: 클라우드 DB를 쓴다고 튜닝 책임이 사라지는 게 아니고, OLTP와 OLAP는 애초에 다른 DB로 분리하는 게 정석이다. 벡터 DB는 어렵게 생각하지 말고 "의미 기반 검색이 필요한 곳에 붙이는 확장 기능" 정도로 접근하면 된다. 마지막 편에서는 실무에서 가장 소홀해지기 쉬운 영역, 보안과 백업·모니터링을 다룬다.
