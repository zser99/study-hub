# 정규화를 깨야 할 때, 그리고 DB 안에서 로직을 돌려야 할 때

지금까지는 "정규화를 지키자", "WHERE 조건 확인하자" 같은 원칙 위주였다. 그런데 실무는 늘 원칙대로만 흘러가지 않는다. 대시보드 하나 띄우려고 다섯 개 테이블을 조인하다가 응답이 5초씩 걸리는 순간, "이걸 정규화대로 계속 지켜야 하나" 하는 고민이 든다. 오늘은 정규화를 의도적으로 깨는 반정규화와 샤딩, 그리고 DB 안에서 로직을 자동으로 돌리는 프로시저·트리거를 다룬다.

## 반정규화 — 읽기 성능을 위한 의도적인 타협

정규화를 철저히 지킨 구조는 데이터 무결성엔 유리하지만, 조회할 때마다 여러 테이블을 조인해야 해서 대시보드나 리포트처럼 읽기가 집중되는 상황에서는 오히려 발목을 잡는다. 이럴 때 의도적으로 중복 컬럼이나 집계 컬럼을 추가하는 게 반정규화(Denormalization)다.

무작정 중복을 허용하기보다, 먼저 2편에서 소개한 구체화 뷰(Materialized View)로 안전하게 우회하는 방법을 고려해보자. 원본 테이블은 정규화를 유지한 채, 자주 조회하는 집계 결과만 별도로 저장해두는 방식이다.

```sql
CREATE MATERIALIZED VIEW mv_monthly_sales AS
SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS total_sales
FROM orders GROUP BY 1;

-- 주기적으로 갱신 (스케줄러 필요)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_monthly_sales;
```

정규화 원칙은 OLTP(거래 처리)에, 반정규화·구체화 뷰는 OLAP(분석·리포팅)에 각각 어울린다고 기억해두면 판단이 쉬워진다.

## 샤딩 — 한 대로 안 될 때

서비스가 한 대의 DB 서버로 감당 못 할 만큼 커지면 여러 서버에 데이터를 나눠 저장하는 샤딩을 고려하게 된다. 같은 DB 안에서 논리적으로 나누는 파티셔닝과 달리, 샤딩은 물리적으로 다른 서버에 분산하기 때문에 수평 확장이 가능하다. 대신 서로 다른 샤드에 걸친 조인이 불가능하고 분산 트랜잭션 관리가 까다롭다는 대가가 따른다.

그래서 실무 조언은 명확하다. 샤딩을 도입하기 전에, 파티셔닝이나 읽기 전용 복제본(Read Replica)만으로 충분히 해결되는지 먼저 검토하라는 것이다. 샤딩은 "정말 필요할 때 쓰는 마지막 카드"에 가깝다.

여러 개의 작은 서비스로 나누는 마이크로서비스 아키텍처(MSA)에서는 각 서비스가 자기 DB를 갖는 게 원칙이다. 이때 여러 서비스에 걸친 작업을 처리하려고 실패 시 보상 트랜잭션으로 되돌리는 사가(Saga) 패턴, 읽기·쓰기 모델을 분리하는 CQRS, 트랜잭션 안에서 이벤트 발행까지 함께 보장하는 아웃박스(Outbox) 패턴이 자주 쓰인다.

## DB 안에서 로직을 실행하기: 프로시저와 트리거

스토어드 프로시저와 함수는 여러 SQL 문을 DB 안에 미리 저장해두고 호출하는 방식이다. 프로시저는 트랜잭션 제어가 가능해 "재고 확인 → 주문 생성 → 재고 차감"처럼 여러 단계를 하나의 단위로 묶는 데 적합하고, 함수는 계산 결과를 반환하는 데 특화돼 `SELECT` 문 안에서 값을 변환하는 용도로 쓰인다.

```sql
CREATE OR REPLACE PROCEDURE sp_create_order(p_customer_id BIGINT, p_product_id INT, p_qty INT)
LANGUAGE plpgsql AS $$
DECLARE v_stock INT;
BEGIN
  SELECT stock_qty INTO v_stock FROM products WHERE id = p_product_id FOR UPDATE;
  IF v_stock < p_qty THEN
    RAISE EXCEPTION '재고 부족: product_id=%', p_product_id;
  END IF;
  INSERT INTO orders (customer_id, product_id, qty) VALUES (p_customer_id, p_product_id, p_qty);
  UPDATE products SET stock_qty = stock_qty - p_qty WHERE id = p_product_id;
END;$$;
```

다만 자주 바뀌는 비즈니스 로직까지 DB 안에 넣으면 유지보수가 어려워진다. 공통적이고 잘 바뀌지 않는 계산 로직에 한정해서 쓰는 게 일반적인 원칙이다.

트리거는 데이터 변경(삽입·수정·삭제)이 일어날 때 DB가 자동으로 실행하는 코드로, 변경 이력을 남기는 감사 로그나 재고가 음수로 안 가게 막는 용도로 유용하다.

```sql
CREATE OR REPLACE FUNCTION trg_audit() RETURNS trigger AS $$
BEGIN
  INSERT INTO audit_log(table_name, op, row_json) VALUES ('orders', TG_OP, to_jsonb(NEW));
  RETURN NEW;
END$$ LANGUAGE plpgsql;

CREATE TRIGGER orders_ai AFTER INSERT ON orders
FOR EACH ROW EXECUTE FUNCTION trg_audit();
```

다만 트리거 안에서 외부 API를 호출하거나 트리거끼리 서로를 호출하는 구조는 장애 전이와 디버깅의 어려움으로 이어지기 쉬워 피하는 게 좋다. 데이터 변경을 실시간으로 다른 시스템에 전파해야 한다면, 트리거보다는 DB의 변경 로그를 읽어 이벤트로 흘려보내는 CDC(Change Data Capture) 방식이 더 안정적인 대안이다.

**오늘의 한 줄 요약**: 반정규화·샤딩은 "정규화가 틀려서"가 아니라 "읽기 성능·확장성과의 타협"이다. 무작정 깨기 전에 구체화 뷰나 파티셔닝으로 해결되는지 먼저 확인하자. 다음 편에서는 클라우드 DB와 벡터 검색·AI 시대의 DB 트렌드를 다룬다.
