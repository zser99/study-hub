# 서비스를 지키는 건 기능이 아니라 이런 디테일이다 — 보안·백업·모니터링

이 시리즈의 마지막 편이다. 지금까지 설계와 쿼리, 성능 얘기를 했다면, 오늘은 "터지면 진짜 큰일 나는" 영역인 보안, 백업, 모니터링을 다룬다. 화려하진 않지만 서비스를 실제로 지키는 건 이런 디테일이다.

## 누가 무엇을 할 수 있는가: 인증과 권한

DB 보안은 "누가 접속했는가"를 확인하는 인증(Authentication)과 "그 사람이 뭘 할 수 있는가"를 정하는 인가(Authorization)로 나뉜다. 실무에서는 사용자마다 권한을 하나씩 부여하는 대신, "분석가는 조회만", "애플리케이션 계정은 정해진 뷰만"처럼 역할(Role)을 먼저 설계하고 사용자를 그 역할에 배정하는 RBAC(역할 기반 접근 제어)를 쓴다. 원칙은 각 역할에 실제로 필요한 권한만 주는 최소 권한 원칙이다.

```sql
CREATE ROLE app_reader NOLOGIN;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_reader;

CREATE ROLE app_user LOGIN PASSWORD 'secret';
GRANT app_reader TO app_user;
```

같은 테이블이라도 고객마다 자기 데이터만 보게 하고 싶다면, PostgreSQL의 행 단위 보안(Row-Level Security)처럼 행 단위로 접근을 제한하는 기능을 쓸 수 있다. 멀티테넌트 서비스를 만든다면 알아둘 만하다.

## SQL 인젝션 — 가장 오래됐고 여전히 흔한 공격

사용자 입력을 SQL 문자열에 그대로 이어붙이면, 공격자가 입력값 안에 악의적인 SQL을 끼워 넣어 DB 구조 자체를 조작할 수 있다. 국제 웹 보안 표준 기구 OWASP는 이를 막는 가장 확실한 방법으로 파라미터 바인딩(Prepared Statement)을 꼽는다.

```python
# 절대 금지: 문자열을 직접 이어붙임
sql = f"SELECT * FROM users WHERE name = '{user_input}'"

# 항상 이렇게: 파라미터 바인딩
cur.execute("SELECT * FROM users WHERE name = %s", (user_input,))
```

이 방식은 SQL 구조와 사용자가 입력한 값을 DB 프로토콜 수준에서 분리하기 때문에, 입력값에 어떤 내용이 들어있든 SQL 코드로 해석되지 않는다. 대부분의 ORM은 기본적으로 파라미터 바인딩을 쓰지만, ORM 안에서도 문자열을 직접 이어붙여 원시 SQL을 실행하면 똑같이 취약해진다는 건 꼭 기억하자. 정렬 기준 컬럼처럼 파라미터로 바인딩하기 어려운 값은 허용된 값 목록(화이트리스트)으로 검증한 뒤 써야 한다.

```python
if order_col not in ('name', 'created_at'):
    order_col = 'created_at'  # 화이트리스트 검증
sql = f"SELECT * FROM items ORDER BY {order_col}"
```

민감한 데이터를 다룬다면 네트워크 전송 구간을 암호화하는 TLS는 기본으로 켜두고, 필요하면 디스크 데이터 전체를 암호화하는 TDE나 주민등록번호처럼 특히 민감한 컬럼만 골라 암호화하는 것도 고려하자.

## 백업, 복구, 그리고 서비스가 멈추지 않게 하기

데이터를 지키는 기본은 백업이다. 전체를 통째로 복사하는 전체 백업과, 마지막 백업 이후 바뀐 부분만 저장하는 증분 백업을 함께 활용하며, "3개의 복사본을 2종류의 매체에, 1곳은 원격지에 보관한다"는 3-2-1 원칙이 널리 쓰인다.

실수로 데이터를 잘못 지웠을 때는 문제가 생기기 직전 시점으로 되돌리는 시점 복구(PITR)가 유용하다. 이건 1편에서 다룬 WAL 로그를 순서대로 다시 실행하는 원리를 그대로 활용한다. 즉 WAL을 제대로 이해하고 있으면 장애 복구도 훨씬 덜 무섭게 느껴진다.

서비스가 끊기지 않게 하려면 주 DB(Primary)의 내용을 실시간으로 대기 서버(Standby)에 복제해두고, 장애 발생 시 자동으로 대기 서버가 역할을 이어받는 장애 조치(Failover) 체계를 갖춘다. 이때 데이터 손실을 어디까지 허용할지(RPO)와 서비스가 멈춰도 되는 최대 시간(RTO)을 미리 정해두고, 그에 맞는 복제 방식과 백업 주기를 설계하는 게 핵심이다.

## 모니터링: 데이터베이스의 건강 상태 확인하기

DB를 사람 건강에 비유하면, 초당 처리하는 트랜잭션 수(TPS)와 질의 수(QPS)는 심장 박동수에, 요청부터 응답까지 걸리는 지연시간(Latency)은 혈압에, 로그는 건강 기록에 해당한다. 온프레미스에서는 Prometheus로 지표를 수집하고 Grafana로 시각화하는 조합이 널리 쓰이고, 클라우드에서는 AWS CloudWatch나 GCP Cloud Monitoring이 별도 설정 없이도 기본 지표를 자동 수집해준다.

```sql
-- PostgreSQL: 30초 이상 걸리고 있는 쿼리 확인
SELECT pid, now() - query_start AS duration, query
FROM pg_stat_activity
WHERE state != 'idle' AND now() - query_start > INTERVAL '30 seconds';
```

평균 응답 시간이 기준을 넘거나, 저장 공간이 얼마 안 남았거나, 복제 지연이 길어지는 상황을 미리 알람으로 설정해두면 장애가 커지기 전에 대응할 수 있다.

## 시리즈를 마치며

1편에서 ACID와 WAL로 시작해, 관계형 모델과 정규화, SQL 기초와 분석, 인덱스와 성능 튜닝, 동시성 제어, 고급 설계, 클라우드와 최신 트렌드를 거쳐 오늘 보안·백업·모니터링까지 왔다. 돌아보면 결국 DB 실무의 핵심은 하나로 수렴한다. "데이터의 정합성을 지키면서, 얼마나 빠르고 안전하게 다룰 것인가." 오늘 다룬 보안·백업·모니터링은 화면에 드러나지 않는 영역이라 소홀해지기 쉽지만, 사고가 나면 가장 먼저 원인으로 지목되는 영역이기도 하다. 이 시리즈가 여러분의 다음 장애 대응 시간을 조금이나마 줄여주길 바란다.
