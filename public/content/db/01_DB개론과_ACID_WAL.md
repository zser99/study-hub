# 트랜잭션은 왜 "약속"이라고 부를까 — ACID와 WAL 제대로 이해하기

CRUD를 짜다 보면 어느 순간 이런 궁금증이 생긴다. `UPDATE` 두 번을 하나의 트랜잭션으로 묶으면 대체 내부에서 무슨 일이 일어나는 걸까? 왜 갑자기 커밋이 느려지는 서비스가 있고, 어떤 서비스는 장애가 나도 데이터가 멀쩡할까? 그 답은 대부분 오늘 다룰 두 가지 개념, ACID와 WAL에 있다.

## 왜 관계형 DB가 표준이 됐을까

1970년대까지만 해도 애플리케이션마다 자기만의 파일에 데이터를 저장했다. 문제는 같은 정보가 여러 파일에 중복되고, 두 사람이 동시에 접근하면 데이터가 꼬여버린다는 것이었다. 이 문제를 해결한 게 IBM 연구원 에드거 커드(E. F. Codd)가 1970년에 제안한 관계형 모델이다. 데이터를 표(테이블) 형태로 표현하고 집합 연산으로 다루자는 아이디어였는데, 이게 지금 우리가 매일 쓰는 MySQL, PostgreSQL, Oracle의 뿌리다.

이후 웹 서비스가 전 세계로 퍼지면서 한 대의 서버로는 감당 못 하는 트래픽이 등장했고, 그게 MongoDB 같은 NoSQL과 Aurora·Spanner 같은 분산 DB로 이어졌다. 결국 DB의 역사는 "데이터 정합성을 얼마나 지킬 것인가"와 "얼마나 많은 트래픽을 받을 것인가" 사이에서 균형점을 찾아온 과정이라고 보면 된다.

## 트랜잭션이 지켜야 할 네 가지 약속, ACID

여러 요청이 동시에 몰려도 DB가 신뢰할 수 있는 상태를 유지하려면 지켜야 할 규칙이 있다. 이 네 가지 속성을 ACID라고 부르는데, 1983년 Theo Härder와 Andreas Reuter가 발표한 논문에서 처음 하나의 개념으로 정리됐다.

- **원자성(Atomicity)**: 트랜잭션 안 작업은 전부 성공하거나 전부 실패한다. 계좌 이체에서 출금은 됐는데 입금이 안 되는 상황은 있을 수 없다.
- **일관성(Consistency)**: 트랜잭션이 끝난 뒤에도 제약조건 같은 규칙을 항상 만족한다.
- **격리성(Isolation)**: 동시에 도는 트랜잭션끼리 서로의 중간 상태를 침범하지 않는다.
- **지속성(Durability)**: 커밋된 결과는 서버가 죽어도 사라지지 않는다.

여기서 실무자가 꼭 알아야 할 함정이 하나 있다. ACID는 "교과서적으로는" 모든 DBMS가 지원하지만, 실제 보장 수준은 천차만별이라는 점이다. 예전 MySQL의 MyISAM 엔진은 롤백과 외래키를 지원하지 않아 사실상 ACID를 만족하지 못했다. 지금 기본값인 InnoDB는 완전한 ACID를 지원한다. PostgreSQL과 Oracle은 MVCC(다중 버전 동시성 제어) 방식으로 안정적인 격리를 구현하고, Aurora 같은 클라우드 DB는 스토리지 자체를 여러 곳에 복제해서 장애에 대비한다. 그래서 DB를 고를 때는 "ACID를 지원하나요?"가 아니라 "어느 수준까지 보장하고, 성능과 어떻게 트레이드오프하나요?"를 물어야 맞다.

## 커밋이 안전한 진짜 이유, WAL

`COMMIT`을 날리면 DB가 곧바로 디스크의 실제 데이터 파일을 고칠 것 같지만, 실제로는 그렇지 않다. PostgreSQL, Oracle, MySQL(InnoDB) 같은 대부분의 관계형 DB는 데이터 파일을 건드리기 전에 변경 내용을 로그(저널)에 먼저 기록한다. 이를 WAL(Write-Ahead Logging), 말 그대로 "로그가 먼저"라는 원칙이다.

```sql
BEGIN;
UPDATE account SET balance = balance - 10000 WHERE id = 'A';
-- 1) WAL 버퍼에 변경 내용 기록
-- 2) 메모리(Shared Buffer)에 반영, 디스크 데이터 파일은 아직 그대로
UPDATE account SET balance = balance + 10000 WHERE id = 'B';
COMMIT;
-- COMMIT 로그를 WAL에 기록하고 fsync
-- 실제 데이터 파일 반영은 이후 체크포인트 시점에
```

로그를 먼저 남겨두면 두 가지가 좋다. 첫째, 장애가 나도 로그를 순서대로 다시 실행(Redo)하거나 취소(Undo)해서 안전하게 복구할 수 있다. 둘째, 디스크 여기저기를 무작위로 고치는 대신 로그에 순차적으로만 쓰면 되니 성능도 빠르다. 여러 서버가 데이터를 나눠 갖는 분산 DB에서는 여기서 한 단계 더 나아가 Paxos·Raft 같은 합의 알고리즘을 쓴다. 리더 노드가 기록한 로그에 과반수 노드가 동의해야 커밋이 확정되는 방식이다. 정리하면 WAL은 "하나의 DB 안에서 장애에 대비하는 안전장치"이고, 합의 알고리즘은 "여러 DB가 항상 같은 결과를 보장하는 안전장치"다.

## 동시성 문제는 다음 편 예고

지금까지는 "하나의 트랜잭션"이 안전하게 처리되는 원리를 봤다. 그런데 실무에서 진짜 골치 아픈 건 여러 트랜잭션이 동시에 같은 데이터를 건드릴 때다. 더티 리드, 반복 불가능 읽기, 팬텀 리드 같은 현상이 왜 생기고 격리 수준을 어떻게 골라야 하는지는 트랜잭션·락 편에서 실무 기준과 함께 자세히 다룰 예정이다.

**오늘의 한 줄 요약**: ACID는 DB가 지켜야 할 네 가지 약속이고, WAL은 그 약속 중 지속성(Durability)을 지키기 위한 구체적인 구현 방식이다. 다음 편에서는 이 신뢰할 수 있는 데이터를 어떻게 "테이블"이라는 구조로 설계하는지, 정규화 이야기로 이어간다.
