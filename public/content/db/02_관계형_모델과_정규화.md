# 테이블 하나로 다 몰아넣으면 안 되는 이유 — 관계형 모델과 정규화

주니어 시절 누구나 한 번쯤 이런 테이블을 만든다. 주문 테이블에 고객 이름, 주소, 상품명, 상품 가격을 전부 욱여넣는 식이다. 처음엔 편하다. 그런데 고객이 이사를 가면? 같은 고객의 주소를 열 번 고쳐야 하는 사태가 벌어진다. 오늘은 이런 사고를 막아주는 관계형 모델의 기본기, 키(Key)와 정규화를 정리한다.

## 테이블, 그리고 세 가지 키

관계형 데이터 모델링이란 결국 현실 세계의 데이터를 행(Row)과 열(Column)로 이루어진 표로 바꾸는 작업이다. 이때 테이블 사이의 관계를 정확히 표현하려고 세 가지 키 개념을 쓴다.

| 키 종류 | 의미 | 특징 |
|---|---|---|
| 기본키(PK) | 각 행을 고유하게 식별하는 컬럼 | NULL·중복 불가, 자동으로 인덱스 생성 |
| 외래키(FK) | 다른 테이블의 기본키를 참조하는 컬럼 | 테이블 간 관계 표현, 참조 무결성 보장 |
| 고유키(UK) | 중복을 허용하지 않는 컬럼 | PK와 달리 NULL은 허용 |

테이블 간 관계는 학생과 학생증처럼 하나씩만 짝지어지는 1:1, 학생 한 명이 여러 과목 성적을 갖는 1:N, 학생과 강좌처럼 서로 여러 건씩 얽히는 N:M으로 나뉜다. 여기서 N:M은 관계형 DB에서 직접 표현할 수 없다. 그래서 두 테이블의 키를 함께 갖는 교차 테이블(가령 "수강" 테이블)을 하나 더 만들어서 푼다. 실무에서 다대다 관계를 보면 반사적으로 "중간 테이블이 필요하겠구나"라고 떠올릴 수 있으면 절반은 성공이다.

## 정규화 — 중복을 줄이는 단계별 규칙

앞서 예로 든 "주문 테이블에 고객 정보까지 다 넣기"처럼 데이터를 한 테이블에 몰아넣으면 세 가지 이상 현상(Anomaly)이 생긴다.

- **삽입 이상**: 주문이 없는데 고객 정보만 등록하고 싶어도 불필요한 주문 컬럼까지 채워야 한다.
- **삭제 이상**: 마지막 주문 하나를 지웠을 뿐인데 그 고객의 주소 정보까지 통째로 사라진다.
- **갱신 이상**: 같은 고객 주소가 여러 행에 중복 저장돼 있어서, 일부만 고치면 데이터가 서로 어긋난다.

정규화는 이 문제를 막기 위해 테이블을 단계적으로 분리해 나가는 설계 규칙이다. 실무에서는 보통 3단계까지 적용한다.

**1NF**: 모든 컬럼은 더는 쪼갤 수 없는 값(원자값)을 가져야 한다. "수강과목: DB, 네트워크"처럼 한 칸에 여러 값을 넣으면 안 되고, 별도의 행으로 나눠야 한다.

**2NF**: 1NF를 만족하면서, 복합키 중 일부에만 종속된 속성(부분 함수 종속)을 제거한다. (학번, 과목코드)가 기본키인 성적 테이블에서 "학생이름"은 학번에만 종속되므로 별도 테이블로 분리한다.

**3NF**: 2NF를 만족하면서, 기본키가 아닌 속성이 또 다른 비-기본키 속성에 종속되는 이행적 종속을 제거한다. "학번 → 학과코드 → 학과명"처럼 연쇄적으로 종속된다면 학과 정보를 따로 뗀다.

```sql
-- 1NF 위반: 원자값이 아님
CREATE TABLE student_bad (
  student_id INT PRIMARY KEY,
  name VARCHAR(50),
  subjects VARCHAR(200)  -- "DB, 네트워크, OS" ← 문제!
);

-- 1NF~3NF 적용 후
CREATE TABLE students (
  id INT PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  major_id INT REFERENCES majors(id)  -- 학과명 분리 (3NF)
);
CREATE TABLE enrollments (
  student_id INT REFERENCES students(id),
  course_id INT REFERENCES courses(id),
  score DECIMAL(5,2),
  PRIMARY KEY (student_id, course_id)
);
```

3NF보다 더 엄격한 정규형(BCNF·4NF·5NF)도 있지만, 정규화를 과하게 밀어붙이면 조회할 때마다 테이블을 여러 번 조인해야 해서 성능이 떨어질 수 있다. 이럴 땐 의도적으로 중복을 허용하는 반정규화 전략을 함께 검토하는데, 이 부분은 뒤에 고급 설계 편에서 다시 짚는다.

## SQL이냐 NoSQL이냐, 결국 이 질문 하나

정규화까지 배우고 나면 자연스럽게 드는 의문이 "그럼 NoSQL은 왜 쓰는 거지?"다. 관계형 DB(SQL)는 요구사항을 미리 테이블로 정의하고 엄격한 ACID를 지키는 데 강하다. 반면 NoSQL은 스키마가 고정되어 있지 않아 형태가 자주 바뀌는 데이터를 빠르게 저장·검색하는 데 유리한 대신 일관성을 다소 완화한다. 결국 선택 기준은 하나다. "이 데이터가 얼마나 엄격한 트랜잭션 보장을 필요로 하는가." 결제·재고처럼 정확성이 생명인 데이터는 SQL, 로그·세션·추천 콘텐츠처럼 유연성과 처리량이 중요한 데이터는 NoSQL 쪽으로 기우는 게 일반적이다.

**오늘의 한 줄 요약**: 정규화는 "같은 정보를 두 곳에 적지 말자"는 원칙을 지키기 위한 단계별 절차다. 다음 편에서는 이렇게 정리한 테이블을 실제로 어떻게 설계 문서(ERD)로 그리고, 어떤 DBMS를 골라야 하는지 이어서 다룬다.
