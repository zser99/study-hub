# 3강. 객체 지향 프로그래밍

## 학습 목표
절차 지향 프로그래밍에서 객체 지향 프로그래밍으로 코드가 점진적으로 발전하는 과정을 직접 따라가며, 데이터와 기능을 하나로 묶는(캡슐화) 것이 왜 중요한지 이해한다.

## 1. 절차 지향 vs 객체 지향
- **절차 지향 프로그래밍**: "어떻게" 실행할지, 즉 처리 순서를 중심으로 생각하는 방식. 데이터와 그 데이터를 다루는 로직이 분리되어 있다.
- **객체 지향 프로그래밍**: "무엇을" 다룰지, 즉 객체를 중심으로 생각하는 방식. 데이터와 그 데이터를 다루는 기능(메서드)이 하나의 객체 안에 함께 묶여 있다.

둘은 대립 관계가 아니다. 객체 지향으로 짜더라도 결국 코드는 순서대로 실행된다. 차이는 **설계의 초점**이 데이터+기능의 분리에 있느냐, 결합에 있느냐다. 지금까지 우리가 클래스를 써서 데이터를 담는 그릇으로만 활용했다면, 그건 아직 절차 지향에 가깝다. 객체 지향이 되려면 기능(메서드)까지 클래스 안으로 들어와야 한다.

## 2. 예제로 따라가 보기: 선풍기 제어 프로그램
요구사항: 선풍기를 켜고 끌 수 있고, 풍속을 올리고 내릴 수 있고, 현재 상태를 확인할 수 있어야 한다.

### 1단계 - 절차 지향: 변수만 나열
```java
public class FanMain1 {
    public static void main(String[] args) {
        int speed = 0;
        boolean isOn = false;

        isOn = true;
        System.out.println("선풍기를 켭니다");

        speed++;
        System.out.println("현재 풍속: " + speed);

        speed++;
        System.out.println("현재 풍속: " + speed);

        System.out.println("상태 확인 -> ON, 풍속:" + speed);

        isOn = false;
        System.out.println("선풍기를 끕니다");
    }
}
```
순서대로 동작은 하지만, `main` 메서드 하나에 모든 로직이 나열되어 있다. 이 상태로 기능이 늘어나면 코드가 점점 길고 읽기 어려워진다.

### 2단계 - 데이터만 클래스로 묶기
```java
public class FanState {
    int speed;
    boolean isOn;
}
```
```java
public class FanMain2 {
    public static void main(String[] args) {
        FanState state = new FanState();

        state.isOn = true;
        System.out.println("선풍기를 켭니다");

        state.speed++;
        System.out.println("현재 풍속: " + state.speed);
        // ... 이하 동일한 로직 반복
    }
}
```
관련 데이터(`speed`, `isOn`)가 `FanState` 안에 모여 있어 "선풍기 상태"라는 개념이 명확해졌다. 하지만 이 데이터를 다루는 로직은 여전히 `main` 안에 그대로 남아있다.

### 3단계 - 반복되는 로직을 메서드로 추출
로직 중 켜기, 끄기, 풍속 조절, 상태 출력이 반복되거나 재사용될 가능성이 크다. 이를 메서드로 분리하면:
```java
public class FanMain3 {
    public static void main(String[] args) {
        FanState state = new FanState();
        turnOn(state);
        speedUp(state);
        speedUp(state);
        showStatus(state);
        turnOff(state);
    }

    static void turnOn(FanState state) {
        state.isOn = true;
        System.out.println("선풍기를 켭니다");
    }

    static void turnOff(FanState state) {
        state.isOn = false;
        System.out.println("선풍기를 끕니다");
    }

    static void speedUp(FanState state) {
        state.speed++;
        System.out.println("현재 풍속: " + state.speed);
    }

    static void showStatus(FanState state) {
        String status = state.isOn ? "ON" : "OFF";
        System.out.println("상태 확인 -> " + status + ", 풍속:" + state.speed);
    }
}
```
메서드로 나눈 덕분에 로직이 이름을 갖게 되어 읽기 쉬워지고, 중복이 사라지고, 특정 기능을 고칠 때 해당 메서드만 손보면 된다.

### 여기까지의 한계
`FanState`(데이터)와 그 데이터를 다루는 메서드(`FanMain3`)가 여전히 서로 다른 클래스에 나뉘어 있다. 데이터 구조가 바뀌면 이걸 사용하는 메서드들도 전부 손봐야 하고, 관리 포인트가 두 군데로 흩어진다.

## 3. 데이터와 기능을 완전히 하나로: 진짜 객체 지향
클래스는 멤버 변수뿐 아니라 메서드도 함께 담을 수 있다. 선풍기와 관련된 데이터와 기능을 전부 `Fan` 클래스 하나로 옮겨보자.
```java
public class Fan {
    int speed;
    boolean isOn;

    void turnOn() {
        isOn = true;
        System.out.println("선풍기를 켭니다");
    }

    void turnOff() {
        isOn = false;
        System.out.println("선풍기를 끕니다");
    }

    void speedUp() {
        speed++;
        System.out.println("현재 풍속: " + speed);
    }

    void showStatus() {
        String status = isOn ? "ON" : "OFF";
        System.out.println("상태 확인 -> " + status + ", 풍속:" + speed);
    }
}
```
사용하는 쪽 코드는 훨씬 단순해진다.
```java
public class FanMain4 {
    public static void main(String[] args) {
        Fan fan = new Fan();
        fan.turnOn();
        fan.speedUp();
        fan.speedUp();
        fan.showStatus();
        fan.turnOff();
    }
}
```
이제 `Fan` 객체 하나만 생성하면 끝이다. `fan.speed`, `fan.isOn`이라는 내부 데이터가 어떻게 구성되어 있는지 사용하는 입장에서는 전혀 몰라도 된다. `Fan`이 제공하는 메서드만 호출하면 된다.

**참고**: 메서드 안에서 `speed`, `isOn`처럼 앞에 아무것도 안 붙이고 멤버 변수에 접근하면, 자바는 자동으로 "이 메서드를 호출한 객체 자신의" 멤버 변수로 인식한다. 즉 `fan.speedUp()`을 호출하면, `speedUp()` 메서드 내부의 `speed`는 바로 그 `fan` 객체의 `speed`를 가리킨다.

## 4. 캡슐화
`Fan` 클래스처럼 속성(데이터)과 기능(메서드)을 하나로 묶고, 외부에는 필요한 기능만 메서드 형태로 공개하는 것을 **캡슐화(Encapsulation)**라 한다. 캡슐화의 이점:
- **사용이 쉬워진다**: 내부 데이터 구조를 몰라도 메서드만 호출하면 된다.
- **변경에 강해진다**: 클래스 내부 구현(필드명, 로직)을 바꿔도, 메서드 이름과 사용법이 그대로면 그 클래스를 사용하는 다른 코드는 전혀 손댈 필요가 없다.
- **가독성이 좋아진다**: 관련된 것들이 한 군데 모여 있어 코드를 이해하기 쉽다.

## 5. 객체란 무엇인가
세상의 사물을 단순화하면 대부분 "속성(데이터)"과 "기능"으로 표현할 수 있다.

| 대상 | 속성 | 기능 |
|---|---|---|
| 자전거 | 현재 기어 단수, 속도 | 페달 밟기, 브레이크 잡기, 기어 변경 |
| 스마트폰 | 배터리 잔량, 화면 밝기 | 전원 켜기/끄기, 밝기 조절 |
| 게임 캐릭터 | 레벨, 체력, 소지 아이템 | 이동, 공격, 아이템 획득 |

객체 지향 프로그래밍은 이런 대상들을 "속성 + 기능을 가진 객체"로 모델링하는 방식이다. 다만 실세계 사물과 코드의 객체가 항상 1:1로 정확히 대응하는 것은 아니며, 프로그램이 필요로 하는 만큼만 속성과 기능을 뽑아서 설계한다.

3. 캡슐화의 이점을 하나 이상 말해보자.

<details>
<summary>정답 확인</summary>

1. 절차 지향은 데이터와 그 데이터를 다루는 기능이 분리되어 있고, 객체 지향은 이 둘이 하나의 객체 안에 묶여 있다.
2. 메서드 안에서 아무 접두사 없이 멤버 변수에 접근하면, 자바는 그 메서드를 호출한 객체 자신의 멤버 변수로 자동 인식하기 때문이다.
3. 내부 구현을 몰라도 사용할 수 있고, 내부 구현이 바뀌어도 사용하는 쪽 코드를 바꿀 필요가 없으며, 관련된 데이터와 기능이 한 곳에 모여 가독성이 좋아진다.

## 핵심 정리
| 개념 | 설명 |
|---|---|
| 절차 지향 | 데이터와 기능이 분리, 실행 순서 중심 |
| 객체 지향 | 데이터와 기능을 하나의 객체로 결합 |
| 캡슐화 | 속성+기능을 묶고 필요한 기능만 외부에 공개 |
| 메서드 내부의 멤버 변수 | 그 메서드를 호출한 객체 자신의 멤버 변수를 가리킴 |
