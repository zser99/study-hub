# 5강. 패키지와 접근 제어자

## 학습 목표
클래스가 많아질 때 이를 정리하는 패키지의 역할과, 클래스 내부 데이터를 외부로부터 안전하게 보호하는 접근 제어자의 역할을 이해한다.

## 1. 패키지가 필요한 이유
카페 주문 시스템을 만든다고 해보자. 처음엔 `MenuItem`, `Order` 클래스 몇 개면 충분하지만, 기능이 늘어나면 `MenuItem`, `MenuCategory`, `Order`, `OrderHistory`, `Payment`, `Receipt`, `Member`, `MemberGrade` 등 클래스 수가 금방 수십 개로 불어난다. 이렇게 많은 클래스를 관리하려면 관련 있는 것끼리 묶어서 분류할 방법이 필요하다.

컴퓨터가 파일을 폴더(디렉토리)로 분류하듯, 자바는 **패키지(package)**라는 개념으로 클래스를 분류한다.
```
cafe.menu
    MenuItem
    MenuCategory
cafe.order
    Order
    OrderHistory
cafe.payment
    Payment
    Receipt
```

### 패키지 사용법
패키지를 만들고 그 안에 클래스를 넣는다. 코드 첫 줄에 `package 패키지명;`을 적으면 그 파일의 클래스가 해당 패키지에 속하게 된다. **패키지 이름과 실제 폴더 위치는 반드시 일치해야 한다.**
```java
// cafe/menu/MenuItem.java
package cafe.menu;

public class MenuItem {
    public MenuItem() {
        System.out.println("cafe.menu 패키지의 MenuItem 생성");
    }
}
```
```java
// cafe/order/Order.java
package cafe.order;

public class Order {
    public Order() {
        System.out.println("cafe.order 패키지의 Order 생성");
    }
}
```
다른 패키지에 있는 클래스를 쓰려면 전체 경로(`cafe.menu.MenuItem`)를 적거나, `import`로 미리 선언해두고 클래스 이름만 써도 된다.
```java
package cafe.order;

import cafe.menu.MenuItem;

public class OrderMain {
    public static void main(String[] args) {
        MenuItem item = new MenuItem();   // import 덕분에 패키지명 생략 가능
        Order order = new Order();        // 같은 패키지라 경로 생략 가능
    }
}
```
특정 패키지의 모든 클래스를 쓰고 싶다면 `import cafe.menu.*;`처럼 `*`(별)을 쓸 수 있다.

### 같은 이름의 클래스 구분
패키지가 다르면 클래스 이름이 같아도 문제없다. `cafe.menu.Receipt`와 `cafe.payment.Receipt`가 동시에 있어도, 패키지 이름으로 구분되기 때문이다. 다만 한 파일에서 이름이 같은 두 클래스를 동시에 `import`할 수는 없다. 하나만 `import`하고 나머지는 전체 경로로 적어야 한다.

### 패키지 규칙
- 패키지 이름과 폴더(디렉토리) 위치는 반드시 일치해야 한다. (필수)
- 패키지 이름은 관례상 모두 소문자를 사용한다.
- 이름 충돌을 피하려고 보통 회사 도메인을 거꾸로 붙인다 (예: `com.mycompany.cafe`). 필수는 아니지만, 외부에 공개하는 라이브러리라면 지키는 게 좋다.
- 패키지가 `a`, `a.b`, `a.c`처럼 계층 구조로 보여도, `a`와 `a.b`는 서로 완전히 다른 패키지다. `a` 패키지에서 `a.b`의 클래스를 쓰려면 `import`가 필요하다.

## 2. 접근 제어자가 필요한 이유
온도조절기(Thermostat)를 만든다고 하자. 안전을 위해 온도는 항상 5~35도 사이여야 한다.
```java
public class Thermostat {
    int temperature;

    void increase() {
        if (temperature < 35) {
            temperature += 5;
        } else {
            System.out.println("더 이상 온도를 올릴 수 없습니다.");
        }
    }
}
```
`increase()` 메서드는 온도가 35도를 넘지 않도록 안전장치를 걸어뒀다. 하지만 이 안전장치는 무의미하다. `temperature` 필드가 그대로 노출되어 있어서, 사용하는 쪽에서 `thermostat.temperature = 999;`처럼 필드에 직접 접근해 안전 범위를 완전히 무시해버릴 수 있기 때문이다.

이 문제를 근본적으로 막으려면, `temperature` 필드 자체를 클래스 외부에서 아예 건드릴 수 없게 막아야 한다. 이때 쓰는 것이 **접근 제어자(access modifier)**다.
```java
public class Thermostat {
    private int temperature;   // 외부 직접 접근 차단

    void increase() {
        if (temperature < 35) {
            temperature += 5;
        } else {
            System.out.println("더 이상 온도를 올릴 수 없습니다.");
        }
    }
}
```
```java
thermostat.temperature = 999;  // 컴파일 오류! private 필드는 외부에서 접근 불가
```
`private`이 붙으면 그 필드는 오직 클래스 내부에서만 접근할 수 있다. 이제 온도를 바꾸는 유일한 방법은 `increase()`처럼 클래스가 공식적으로 제공하는 메서드뿐이다.

## 3. 접근 제어자 4종류
| 접근 제어자 | 범위 |
|---|---|
| `private` | 같은 클래스 내부에서만 접근 가능 |
| (기본값, 지정 안 함) `package-private` | 같은 패키지 안에서 접근 가능 |
| `protected` | 같은 패키지 + 상속 관계에서 접근 가능 (상속은 7강에서 다룸) |
| `public` | 어디서든 접근 가능 |

허용 범위가 좁은 순서: `private → package-private → protected → public`. 필드, 메서드, 생성자 모두에 붙일 수 있다. 클래스 자체(클래스 레벨)에는 `public`과 `package-private`(생략)만 붙일 수 있고, `private`, `protected`는 클래스 레벨에는 쓸 수 없다.

**참고**: 접근 제어자를 아무것도 안 쓰면 "기본값"이 적용되는데, 이를 흔히 `default`라 부르지만 실제로는 "같은 패키지 안에서만 보인다"는 뜻이라 **package-private**이라는 표현이 더 정확하다.

## 4. 캡슐화 완성하기: 무엇을 숨기고 무엇을 공개할까
- **데이터는 숨겨라**: 필드를 외부에 그대로 노출하면, 클래스가 정성껏 만들어둔 검증 로직을 다 건너뛰고 값을 마음대로 바꿀 수 있다. 그래서 필드는 대부분 `private`으로 막고, 꼭 필요한 경우에만 메서드를 통해 값을 읽거나 바꾸게 한다.
- **내부 전용 기능도 숨겨라**: 클래스 내부에서만 쓰는 보조 메서드(검증 로직 등)를 외부에 공개하면, 사용하는 쪽에서 "이 메서드를 언제 호출해야 하지?" 같은 불필요한 고민을 하게 된다. 외부에는 꼭 필요한 기능만 `public`으로 공개하고, 나머지는 `private`으로 숨긴다.

돼지저금통(PiggyBank)을 예로 잘 캡슐화된 클래스를 만들어보자.
```java
public class PiggyBank {
    private int balance;

    public PiggyBank() {
        balance = 0;
    }

    public void deposit(int amount) {
        if (isValidAmount(amount)) {
            balance += amount;
        } else {
            System.out.println("유효하지 않은 금액입니다.");
        }
    }

    public void withdraw(int amount) {
        if (isValidAmount(amount) && balance - amount >= 0) {
            balance -= amount;
        } else {
            System.out.println("유효하지 않은 금액이거나 잔액이 부족합니다.");
        }
    }

    public int getBalance() {
        return balance;
    }

    // 내부에서만 쓰는 검증 로직 -> 외부에 노출할 필요 없음
    private boolean isValidAmount(int amount) {
        return amount > 0;
    }
}
```
`PiggyBank`를 사용하는 입장에서는 `deposit`, `withdraw`, `getBalance` 딱 3개 메서드만 알면 된다. `balance` 필드와 `isValidAmount()` 검증 로직은 내부에 숨어있어, 사용하는 쪽에서 신경 쓸 필요도 없고 실수로 망가뜨릴 수도 없다. 만약 `balance`를 `public`으로 열어뒀다면, 누군가 `piggyBank.balance = 999999;`처럼 검증을 통째로 우회할 수 있었을 것이다.

## 핵심 정리
| 개념 | 설명 |
|---|---|
| 패키지 | 관련 있는 클래스를 묶어서 분류하는 단위, 폴더 구조와 일치해야 함 |
| import | 다른 패키지의 클래스를 경로 생략하고 쓸 수 있게 함 |
| private | 클래스 내부에서만 접근 가능 |
| package-private(기본값) | 같은 패키지 안에서 접근 가능 |
| protected | 같은 패키지 + 상속 관계에서 접근 가능 |
| public | 어디서든 접근 가능 |
| 캡슐화 원칙 | 데이터는 숨기고, 꼭 필요한 기능만 공개 |
