# 8강. 다형성 1 - 캐스팅과 오버라이딩

## 학습 목표
객체지향의 꽃이라 불리는 다형성의 두 핵심 축, 다형적 참조와 메서드 오버라이딩을 이해하고, 캐스팅·instanceof를 다룰 수 있게 된다.

## 1. 다형성이란
다형성(Polymorphism)은 "여러 형태"라는 뜻으로, 하나의 객체(정확히는 하나의 참조 변수)가 여러 타입으로 다뤄질 수 있는 능력을 말한다. 다형성을 제대로 이해하려면 두 가지 핵심 이론이 필요하다.
- **다형적 참조**: 부모 타입의 변수 하나로 다양한 자식 인스턴스를 참조할 수 있는 것
- **메서드 오버라이딩**: 자식이 부모의 기능을 재정의하는 것 (7강에서 다룸)

## 2. 다형적 참조: 부모는 자식을 담을 수 있다
```java
public class Employee {
    public void work() {
        System.out.println("업무를 합니다.");
    }
}

public class Manager extends Employee {
    public void manage() {
        System.out.println("팀을 관리합니다.");
    }
}
```
```java
Employee e1 = new Employee();   // 부모 타입 -> 부모 인스턴스
e1.work();

Manager m1 = new Manager();     // 자식 타입 -> 자식 인스턴스
m1.work();
m1.manage();

Employee e2 = new Manager();    // 부모 타입 변수 -> 자식 인스턴스 (다형적 참조)
e2.work();
// e2.manage();  // 컴파일 오류! Employee 타입에는 manage()가 없음
```
`Employee e2 = new Manager();`처럼 **부모 타입의 변수는 자식 인스턴스를 담을 수 있다.** 이것이 다형적 참조다. 반대로 `Manager m = new Employee();`는 불가능하다 — 자식은 부모를 담을 수 없다.

**왜 가능한가**: `new Manager()`를 하면 메모리에는 `Manager`뿐 아니라 부모인 `Employee` 부분까지 함께 생성된다. `Employee` 타입 변수는 그 인스턴스 안에서 자신의 타입(`Employee`)에 해당하는 부분만 보고 사용하는 것이라 문제가 없다.

**한계**: `e2`의 타입은 어디까지나 `Employee`이므로, `Manager`에만 있는 `manage()`는 호출할 수 없다 — 컴파일 오류가 난다. 이걸 호출하려면 캐스팅이 필요하다.

## 3. 캐스팅
### 업캐스팅 (자식 → 부모)
자식 타입을 부모 타입으로 취급하는 것으로, 안전하기 때문에 생략도 가능하다.
```java
Manager m = new Manager();
Employee e = (Employee) m;   // 명시적 업캐스팅
Employee e2 = m;             // 업캐스팅은 생략 가능 (권장)
```
어떤 인스턴스든 생성될 때 부모 부분이 항상 함께 만들어지므로, 업캐스팅은 항상 안전하다.

### 다운캐스팅 (부모 → 자식)
부모 타입 변수를 다시 자식 타입으로 되돌리는 것으로, 반드시 명시적으로 `(타입)`을 붙여야 한다.
```java
Employee e = new Manager();      // 다형적 참조
Manager m = (Manager) e;         // 다운캐스팅
m.manage();

// 메서드 호출 순간만 임시로 다운캐스팅할 수도 있다
((Manager) e).manage();
```
**다운캐스팅은 위험할 수 있다.** 실제로 생성된 인스턴스가 그 자식 타입이 맞는 경우에만 성공한다.
```java
Employee e3 = new Employee();     // 진짜 Employee로 생성됨 (Manager 부분 없음)
Manager m3 = (Manager) e3;        // 컴파일은 되지만 실행 시점에 오류!
// ClassCastException 발생
```
`e3`은 애초에 `Manager`로 생성된 적이 없으므로, 메모리 어디에도 `Manager` 부분이 없다. 이런 경우 자바는 `ClassCastException`이라는 **런타임 오류**를 발생시킨다. 컴파일 오류와 달리 런타임 오류는 프로그램이 실제로 실행되는 도중에 터지기 때문에 더 위험하다. 그래서 다운캐스팅은 개발자가 "이게 안전한지 내가 책임진다"는 의미로 명시적으로 적어주게 되어 있다.

## 4. instanceof: 안전하게 다운캐스팅하기
다운캐스팅 전에, 참조하는 인스턴스가 정말 그 타입이 맞는지 `instanceof`로 미리 확인하면 안전하다.
```java
static void process(Employee e) {
    e.work();
    if (e instanceof Manager) {
        Manager m = (Manager) e;
        m.manage();
    }
}
```
`e instanceof Manager`는 `e`가 참조하는 실제 인스턴스가 `Manager` 타입(또는 그 자식)이면 `true`를 반환한다. 즉 "오른쪽 타입의 자리에 왼쪽 인스턴스가 들어갈 수 있는가"를 대입 가능 여부로 생각하면 쉽다.

**자바 16 이상의 패턴 매칭**: `instanceof`로 확인함과 동시에 변수까지 선언할 수 있다.
```java
if (e instanceof Manager m) {
    m.manage();   // 캐스팅 없이 바로 사용 가능
}
```

## 5. 다형성의 핵심: 필드는 오버라이딩되지 않지만, 메서드는 된다
이제 다형적 참조와 메서드 오버라이딩을 합쳐보자. 여기가 다형성의 진짜 힘이 드러나는 지점이다.
```java
public class Employee {
    public String role = "직원";
    public void greet() {
        System.out.println("Employee.greet");
    }
}

public class Manager extends Employee {
    public String role = "관리자";   // 부모와 같은 이름의 필드

    @Override
    public void greet() {
        System.out.println("Manager.greet");
    }
}
```
```java
Employee poly = new Manager();
System.out.println(poly.role);  // "직원"  <- 필드는 선언 타입(Employee) 기준
poly.greet();                   // "Manager.greet"  <- 메서드는 오버라이딩된 것이 우선
```
- **필드(멤버 변수)는 오버라이딩되지 않는다.** `poly.role`을 읽으면, `poly`의 **선언된 타입**인 `Employee`에 있는 `role`을 그대로 읽는다. 실제 인스턴스가 `Manager`라는 사실은 필드 접근에 영향을 주지 않는다.
- **메서드는 오버라이딩된다.** `poly.greet()`를 호출하면 일단 `Employee` 타입에서 `greet()`를 찾지만, 하위 타입인 `Manager`가 이를 오버라이딩했다면 **오버라이딩된 메서드가 항상 우선권을 가진다.** 그래서 실제로는 `Manager.greet()`가 실행된다.

이 성질 덕분에, 부모 타입의 변수 하나로 다양한 자식 객체들을 다루면서도, 실행되는 동작은 각 객체의 실제 타입(자식)에 맞게 자동으로 달라진다. 이것이 다형성을 실무에서 유용하게 만드는 핵심 원리다.

## 핵심 정리
| 개념 | 설명 |
|---|---|
| 다형적 참조 | 부모 타입 변수가 자식 인스턴스를 참조하는 것 |
| 업캐스팅 | 자식 → 부모로 타입 변경, 생략 가능, 항상 안전 |
| 다운캐스팅 | 부모 → 자식으로 타입 변경, 명시 필요, 실패 시 ClassCastException |
| instanceof | 실제 인스턴스가 특정 타입인지 확인 |
| 필드 | 선언한 변수의 타입 기준으로 접근 (오버라이딩 X) |
| 메서드 | 실제 인스턴스에서 오버라이딩된 메서드가 항상 우선 실행 |
