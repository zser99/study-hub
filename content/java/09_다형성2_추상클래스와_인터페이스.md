# 9강. 다형성 2 - 추상 클래스와 인터페이스

## 학습 목표
다형적 참조와 오버라이딩만으로는 막을 수 없는 두 가지 설계 문제를 이해하고, 이를 해결하는 추상 클래스와 인터페이스의 개념·차이·다중 구현을 익힌다.

## 1. 다형성만으로는 부족한 두 가지 문제
결제 수단을 표현하는 클래스를 만든다고 해보자.
```java
public class PaymentMethod {
    public void pay(int amount) {
        System.out.println("결제 방식이 정해지지 않았습니다.");
    }
}

public class CardPayment extends PaymentMethod {
    @Override
    public void pay(int amount) {
        System.out.println(amount + "원을 카드로 결제합니다.");
    }
}
```
`PaymentMethod pm = new CardPayment();`처럼 다형적 참조를 쓰면 실제 결제 로직은 자식의 오버라이딩된 메서드가 실행된다. 여기까지는 8강에서 다룬 내용 그대로다. 그런데 이 구조에는 두 가지 허점이 있다.

**문제 1. 부모를 직접 생성할 수 있다.** `PaymentMethod`는 "결제 수단"이라는 개념을 표현하기 위한 것일 뿐, 그 자체로는 어떻게 결제할지 정해진 게 없다. 그런데도 `new PaymentMethod()`처럼 부모를 직접 인스턴스로 만들 수 있고, `pay()`를 호출하면 "결제 방식이 정해지지 않았습니다"라는 의미 없는 메시지만 출력된다. 개념적으로만 존재해야 할 타입이 실체를 가져버리는 것이다.

**문제 2. 오버라이딩을 깜빡해도 컴파일러가 잡아주지 못한다.** 새로운 결제 수단 `PointPayment`를 추가하면서 실수로 `pay()`를 오버라이딩하지 않으면 어떻게 될까?
```java
public class PointPayment extends PaymentMethod {
    // pay()를 깜빡하고 작성하지 않음
}
```
```java
PaymentMethod pm = new PointPayment();
pm.pay(1000);   // "결제 방식이 정해지지 않았습니다." <- 컴파일은 되지만 논리적으로 버그
```
컴파일은 멀쩡히 성공하지만, 실제로는 포인트 결제 로직이 전혀 동작하지 않는 채로 배포될 수 있다. 자바는 이 두 가지 문제를 해결하기 위해 **추상 클래스**라는 기능을 제공한다.

## 2. 추상 클래스와 추상 메서드
```java
public abstract class PaymentMethod {

    public abstract void pay(int amount);   // 추상 메서드 - 몸통(body)이 없다

    public void printReceipt(int amount) {  // 일반 메서드 - 몸통이 있다
        System.out.println("[영수증] 결제 금액: " + amount + "원");
    }
}
```
- **추상 클래스(abstract class)**: 클래스 선언에 `abstract`를 붙인다. **인스턴스를 직접 생성할 수 없다.** `new PaymentMethod()`를 시도하면 "PaymentMethod is abstract; cannot be instantiated" 컴파일 오류가 발생한다. 이렇게 문제 1이 원천 차단된다.
- **추상 메서드(abstract method)**: `abstract void pay(int amount);`처럼 몸통 `{ }` 없이 선언부만 있는 메서드다. "이 메서드는 자식이 반드시 구현해야 한다"는 규격만 제공한다.
- 클래스 안에 추상 메서드가 하나라도 있으면, 그 클래스는 반드시 `abstract`로 선언해야 한다.
- 추상 클래스라고 해서 모든 메서드가 추상 메서드일 필요는 없다. `printReceipt()`처럼 몸통이 있는 일반 메서드도 함께 둘 수 있고, 이런 메서드는 자식이 그대로 상속받아 쓴다.

```java
public class CardPayment extends PaymentMethod {
    @Override
    public void pay(int amount) {
        System.out.println(amount + "원을 카드로 결제합니다.");
    }
}
```
자식 클래스가 추상 클래스를 상속하면서 추상 메서드를 구현하지 않으면 어떻게 될까?
```java
public class PointPayment extends PaymentMethod {
    // pay()를 구현하지 않음
}
```
이제는 컴파일 오류가 발생한다 — "PointPayment is not abstract and does not override abstract method pay(int) in PaymentMethod". 이렇게 문제 2도 컴파일 시점에 강제로 걸러진다. `PointPayment`가 정말 추상 메서드를 구현하지 않은 채로 두고 싶다면, `PointPayment` 자신도 `abstract class`로 선언해야 한다.

## 3. 순수 추상 클래스
클래스에 속한 **모든** 메서드가 추상 메서드인 경우를 **순수 추상 클래스**라 부른다.
```java
public abstract class PaymentMethod {
    public abstract void pay(int amount);
    public abstract void printReceipt(int amount);   // 이것도 추상 메서드로 변경
}
```
순수 추상 클래스는 실행 가능한 코드를 전혀 갖지 않는다. 오직 "이런 메서드들을 구현해야 한다"는 설계도(규격) 역할만 한다.
```java
public class CashPayment extends PaymentMethod {
    @Override
    public void pay(int amount) {
        System.out.println(amount + "원을 현금으로 결제합니다.");
    }
    @Override
    public void printReceipt(int amount) {
        System.out.println("[현금 영수증] " + amount + "원");
    }
}
```
`CashPayment`는 `pay()`와 `printReceipt()` 둘 다 직접 구현해야 한다. 하나라도 빠뜨리면 컴파일 오류다.

순수 추상 클래스는 USB 규격처럼 생각하면 이해하기 쉽다. USB 규격에 맞춰 만들어야 마우스든 키보드든 실제 장치로 연결되어 동작하듯, `PaymentMethod`라는 규격에 맞춰 `pay()`와 `printReceipt()`를 구현해야 실제로 동작하는 결제 수단이 된다.

## 4. 인터페이스
자바는 이런 순수 추상 클래스를 더 편리하게 쓸 수 있도록 **인터페이스(interface)**라는 문법을 별도로 제공한다. `class` 대신 `interface` 키워드를 쓴다.
```java
public interface Payable {
    public abstract void pay(int amount);
    public abstract void printReceipt(int amount);
}
```
인터페이스의 메서드는 모두 `public abstract`로 간주되기 때문에, 이 키워드를 생략해서 다음처럼 짧게 쓰는 것이 관례이자 권장 사항이다.
```java
public interface Payable {
    void pay(int amount);
    void printReceipt(int amount);
}
```
인터페이스에 선언하는 멤버 변수는 항상 `public static final`로 취급된다. 즉 값을 한 번 정하면 바꿀 수 없는 상수다.
```java
public interface Payable {
    double MAX_DISCOUNT_RATE = 0.3;   // public static final이 생략된 것
    void pay(int amount);
    void printReceipt(int amount);
}
```

**구현하기**: 클래스가 인터페이스를 사용할 때는 `extends`가 아니라 `implements`를 쓴다.
```java
public class CardPayment implements Payable {
    @Override
    public void pay(int amount) {
        System.out.println(amount + "원을 카드로 결제합니다.");
    }
    @Override
    public void printReceipt(int amount) {
        System.out.println("[카드 영수증] " + amount + "원");
    }
}
```
`CardPayment`는 `Payable`에 선언된 메서드를 전부 오버라이딩해야 한다. 인터페이스 역시 `new Payable()`처럼 직접 인스턴스를 만들 수는 없다.

## 5. 상속 vs 구현 — 왜 다르게 부를까
부모 **클래스**의 기능을 자식이 물려받을 때는 "상속받는다"고 표현하지만, **인터페이스**의 기능을 자식이 물려받을 때는 "구현한다"고 표현한다. 이렇게 용어가 다른 이유가 있다.

상속은 부모가 이미 만들어둔 기능을 그대로 물려받는 것이 핵심이다. 반면 인터페이스는 모든 메서드가 추상 메서드이므로, 애초에 물려받아서 바로 쓸 수 있는 완성된 기능이 없다. 인터페이스에 선언된 메서드들은 이름과 매개변수만 있는 설계도이고, 이 설계도가 실제로 어떻게 동작할지는 구현하는 클래스가 전부 채워 넣어야 한다. 그래서 "상속받는다"가 아니라 "구현한다"고 부른다.

다만 자바 내부적으로 보면 클래스, 추상 클래스, 인터페이스는 모두 `.class` 파일로 다루어지고 동작 방식도 사실상 동일하다. 상속과 구현은 사람이 이해하기 쉽도록 붙인 표현의 차이일 뿐이다.

## 6. 왜 인터페이스를 써야 할까
모든 메서드가 추상 메서드라면 순수 추상 클래스로 만들어도 되고 인터페이스로 만들어도 된다. 그런데도 인터페이스를 따로 두는 이유는 두 가지다.

**제약(규약)**: 인터페이스를 만드는 목적은 "이걸 구현하는 쪽에서는 반드시 이 메서드들을 채워야 한다"는 규약을 강제하는 것이다. 순수 추상 클래스는 이론상 나중에 누군가 몸통이 있는 일반 메서드를 슬쩍 추가할 수 있고, 그러면 더 이상 순수 추상 클래스가 아니게 된다. 인터페이스는 애초에 문법적으로 모든 메서드가 추상 메서드로 강제되기 때문에 이런 문제가 생길 수 없다.

**다중 구현**: 클래스 상속은 부모를 하나만 지정할 수 있다(`extends`는 하나만). 반면 인터페이스는 하나의 클래스가 여러 개를 동시에 구현할 수 있다.

좋은 프로그램은 이런 제약이 있는 프로그램이다.

## 7. 인터페이스의 다중 구현
자바가 클래스의 다중 상속을 막는 이유는, 두 부모가 같은 이름의 메서드를 각자 다르게 구현하고 있으면 자식 입장에서 어느 쪽을 물려받아야 할지 애매해지기 때문이다(다이아몬드 문제). 하지만 인터페이스는 메서드 몸통 자체가 없으므로 이 문제가 생기지 않는다. 실제 동작은 항상 구현하는 클래스 쪽에 있기 때문이다.

```java
public interface Discountable {
    void discount(int amount);
    void summary();
}

public interface Taxable {
    void tax(int amount);
    void summary();   // Discountable과 이름이 같은 메서드
}

public class Invoice implements Discountable, Taxable {
    @Override
    public void discount(int amount) {
        System.out.println(amount + "원 할인 적용");
    }
    @Override
    public void tax(int amount) {
        System.out.println(amount + "원에 대한 세금 계산");
    }
    @Override
    public void summary() {
        System.out.println("Invoice 요약 정보 출력");
    }
}
```
`implements Discountable, Taxable`처럼 쉼표로 여러 인터페이스를 나열하면 다중 구현이 가능하다. `Discountable`과 `Taxable` 둘 다 `summary()`를 갖고 있지만, 실제 몸통은 어느 인터페이스에도 없고 오직 `Invoice`에만 있다. 그래서 `summary()`를 딱 한 번만 구현하면 되고, 어느 부모를 따라야 하는지 애매해지는 문제 자체가 없다.
```java
Discountable d = new Invoice();
d.discount(1000);
d.summary();      // Invoice.summary 실행

Taxable t = new Invoice();
t.tax(1000);
t.summary();      // 역시 Invoice.summary 실행
```
`d`와 `t`는 선언 타입이 다르지만, 실제 인스턴스는 둘 다 같은 `Invoice`이므로 `summary()`를 호출하면 결국 `Invoice`에 오버라이딩된 하나의 구현이 실행된다.

> **참고**: 자바 8부터는 인터페이스도 `default` 키워드를 붙이면 몸통이 있는 메서드를 가질 수 있고, 자바 9부터는 `private` 메서드도 가질 수 있다. 다만 이는 예외적인 상황에서만 쓰는 고급 기능이라, 지금 단계에서는 "인터페이스 = 모든 메서드가 추상 메서드"로 이해하는 것으로 충분하다.

## 8. 클래스 상속과 인터페이스 구현을 함께 쓰기
추상 클래스와 인터페이스는 동시에 사용할 수 있다. 결제 수단 예제로 돌아와서, "환불이 가능한 결제 수단"이라는 조건을 인터페이스로 분리해보자.
```java
public abstract class PaymentMethod {
    public abstract void pay(int amount);

    public void printReceipt(int amount) {   // 공통 기능이라 추상 메서드가 아니다
        System.out.println("[영수증] 결제 금액: " + amount + "원");
    }
}

public interface Refundable {
    void refund(int amount);
}
```
```java
public class CashPayment extends PaymentMethod {
    @Override
    public void pay(int amount) {
        System.out.println(amount + "원을 현금으로 결제합니다.");
    }
}
```
```java
public class CardPayment extends PaymentMethod implements Refundable {
    @Override
    public void pay(int amount) {
        System.out.println(amount + "원을 카드로 결제합니다.");
    }
    @Override
    public void refund(int amount) {
        System.out.println(amount + "원을 카드로 환불합니다.");
    }
}
```
`CardPayment`는 `PaymentMethod`를 상속하면서 동시에 `Refundable`을 구현한다. 클래스 상속(`extends`)은 하나만 가능하고 인터페이스 구현(`implements`)은 여러 개가 가능하므로, 둘을 함께 쓸 때는 반드시 `extends`를 먼저, `implements`를 그 뒤에 적는다. `CashPayment`는 `Refundable`을 구현하지 않았으므로 환불 기능이 없는 결제 수단이 된다 — 즉 "결제 수단인지"와 "환불 가능한지"를 서로 다른 축으로 독립적으로 조합할 수 있다.

```java
public class PaymentMain {
    public static void main(String[] args) {
        CashPayment cash = new CashPayment();
        CardPayment card = new CardPayment();

        processPayment(cash);
        processPayment(card);

        refundPayment(card);   // CashPayment는 Refundable이 아니므로 전달 불가
    }

    // PaymentMethod를 상속한 모든 결제 수단에 사용 가능
    private static void processPayment(PaymentMethod pm) {
        System.out.println("결제 시작");
        pm.pay(10000);
        pm.printReceipt(10000);
        System.out.println("결제 종료");
    }

    // Refundable을 구현한 결제 수단에만 사용 가능
    private static void refundPayment(Refundable r) {
        System.out.println("환불 시작");
        r.refund(10000);
        System.out.println("환불 종료");
    }
}
```
```
결제 시작
10000원을 현금으로 결제합니다.
[영수증] 결제 금액: 10000원
결제 종료
결제 시작
10000원을 카드로 결제합니다.
[영수증] 결제 금액: 10000원
결제 종료
환불 시작
10000원을 카드로 환불합니다.
환불 종료
```

**실행 과정 (`processPayment(card)` 기준)**
1. 매개변수 `pm`의 타입은 `PaymentMethod`이므로, `pm.pay(10000)`을 호출하면 먼저 `PaymentMethod` 타입에서 `pay()`를 찾는다.
2. 실제 인스턴스는 `CardPayment`이고, `CardPayment`가 `pay()`를 오버라이딩했으므로 `CardPayment.pay()`가 실행된다.
3. `pm.printReceipt(10000)`은 `CardPayment`가 따로 오버라이딩하지 않았으므로, 부모인 `PaymentMethod`의 구현이 그대로 실행된다.

**실행 과정 (`refundPayment(card)` 기준)**
1. 매개변수 `r`의 타입은 `Refundable`이다. `r.refund(10000)`을 호출하면 `Refundable` 타입에서 `refund()`를 찾는다.
2. 실제 인스턴스인 `CardPayment`가 `refund()`를 구현했으므로 `CardPayment.refund()`가 실행된다.
3. 만약 `refundPayment(cash)`처럼 `CashPayment`를 넘기려 하면, `CashPayment`는 `Refundable`을 구현하지 않았으므로 애초에 컴파일 오류가 난다.

1. 추상 클래스와 추상 메서드는 각각 어떤 문제를 해결하기 위해 등장했는가?
2. 순수 추상 클래스란 무엇이며, 인터페이스와 어떤 관계인가?
3. 클래스 상속에는 "상속받는다", 인터페이스에는 "구현한다"는 표현을 쓰는 이유는?
4. 클래스는 다중 상속이 안 되는데 인터페이스는 다중 구현이 가능한 이유는?

<details>
<summary>정답 확인</summary>

1. 추상 클래스는 개념적으로만 존재해야 할 부모 타입이 실수로 직접 인스턴스화되는 문제를 막고, 추상 메서드는 자식이 특정 메서드를 오버라이딩하지 않고 넘어가는 것을 컴파일 시점에 강제로 잡아준다.
2. 순수 추상 클래스는 모든 메서드가 추상 메서드인 클래스로, 실행 가능한 코드가 전혀 없는 설계도 역할만 한다. 인터페이스는 이런 순수 추상 클래스를 문법적으로 더 편리하고 안전하게(모든 메서드가 항상 추상 메서드로 강제되도록) 사용할 수 있게 만든 기능이다.
3. 클래스 상속은 부모가 이미 구현해둔 기능을 물려받는 것이 핵심이지만, 인터페이스는 몸통 없는 메서드 이름만 제공하고 실제 구현은 전부 자식이 채워야 하기 때문에 "구현한다"고 표현한다.
4. 인터페이스는 메서드에 실제 몸통(구현)이 없으므로, 같은 이름의 메서드가 여러 인터페이스에 있어도 실행되는 코드는 항상 이를 구현하는 클래스 하나에만 존재한다. 그래서 어떤 부모의 것을 따라야 하는지 애매해지는 다이아몬드 문제가 발생하지 않고, 다중 구현이 허용된다.

</details>

## 핵심 정리
| 개념 | 설명 |
|---|---|
| 추상 클래스 | `abstract class`, 인스턴스화 불가, 추상 메서드와 일반 메서드를 함께 가질 수 있음 |
| 추상 메서드 | 몸통이 없는 메서드, 자식이 반드시 오버라이딩해야 함 |
| 순수 추상 클래스 | 모든 메서드가 추상 메서드인 클래스, 실행 코드가 전혀 없음 |
| 인터페이스 | `interface`, 멤버는 모두 `public abstract`(메서드) / `public static final`(변수)로 취급 |
| 상속 vs 구현 | 클래스는 `extends`로 상속, 인터페이스는 `implements`로 구현 |
| 다중 구현 | 클래스는 부모 하나만 상속 가능, 인터페이스는 여러 개 동시 구현 가능 |
