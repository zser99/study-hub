# 10강. 다형성과 설계, 그리고 다음 학습 로드맵

## 학습 목표
다형성을 실제 설계에 어떻게 활용하는지 "역할과 구현"이라는 관점으로 이해하고, 좋은 객체지향 설계 원칙인 OCP를 익힌 뒤, 앞으로 자바를 어떻게 더 공부해 나가면 좋을지 방향을 잡는다.

## 1. 좋은 객체지향 프로그래밍이란
지금까지 배운 추상화, 캡슐화, 상속, 다형성은 객체지향을 이루는 대표적인 특징들이다. 이 중에서도 실무 설계에 가장 큰 영향을 미치는 것은 **다형성**이다. 스프링 같은 프레임워크의 핵심 원리, 여러 디자인 패턴의 기반이 대부분 다형성에서 출발한다. 이번 강의에서는 다형성을 코드 몇 줄의 문법이 아니라, "설계"의 관점에서 다시 바라본다.

## 2. 역할과 구현이라는 관점
현실 세계를 잘 관찰해보면 "역할"과 그 역할을 "구현"하는 존재가 나뉘어 있는 경우가 많다.
- 프린터로 문서를 출력하고 싶은 사람은 "출력 장치"라는 역할만 알면 된다. 실제로 그 자리에 잉크젯 프린터가 꽂혀 있든, 레이저 프린터가 꽂혀 있든 문서를 보내는 사람의 행동은 달라지지 않는다.
- 오디션에서 "주인공 역할"이 정해져 있으면, 그 역할을 누가 연기하느냐(배우 A든 배우 B든)는 나중에 얼마든지 바뀔 수 있다.
- 채용 공고의 "백엔드 개발자"라는 역할은 고정되어 있지만, 실제로 그 자리에 어떤 사람이 채용되는지는 회사가 필요에 따라 정한다.

이 비유를 코드와 100% 똑같이 매칭할 수는 없지만, "역할"과 "구현"을 나누어 생각하는 습관은 좋은 설계를 이해하는 데 큰 도움이 된다. 역할과 구현을 분리하면 다음과 같은 장점이 생긴다.
- 역할을 사용하는 쪽(클라이언트)은 그 역할의 세부 구현을 몰라도 된다.
- 구현의 내부 로직이 바뀌어도 역할을 사용하는 쪽은 영향을 받지 않는다.
- 구현 자체를 완전히 다른 것으로 교체해도 역할을 사용하는 쪽은 영향을 받지 않는다.

**자바에서는 이 개념을 다형성으로 정확히 구현할 수 있다.** 역할은 **인터페이스**로, 구현은 그 인터페이스를 구현한 **클래스(구현 객체)**로 표현한다.

## 3. 예제로 이해하기 - 역할과 구현을 분리하지 않은 경우
문서를 출력해주는 프로그램을 만든다고 해보자. 처음에는 잉크젯 프린터 하나만 지원하면 된다고 생각해서, 다음과 같이 특정 프린터 클래스에 직접 의존하도록 만들었다.
```java
public class InkjetPrinter {
    public void warmUp() {
        System.out.println("InkjetPrinter.warmUp");
    }
    public void printPage() {
        System.out.println("InkjetPrinter.printPage");
    }
    public void coolDown() {
        System.out.println("InkjetPrinter.coolDown");
    }
}

public class PrintService {
    private InkjetPrinter printer;

    public void setPrinter(InkjetPrinter printer) {
        this.printer = printer;
    }

    public void print() {
        System.out.println("출력을 시작합니다.");
        printer.warmUp();
        printer.printPage();
        printer.coolDown();
    }
}
```
`PrintService`가 `InkjetPrinter`라는 구체적인 클래스에 직접 의존하고 있다. 이 상태에서 레이저 프린터도 지원해야 한다는 요구사항이 생기면 어떻게 될까?
```java
public class PrintService {
    private InkjetPrinter inkjetPrinter;
    private LaserPrinter laserPrinter;   // 추가

    public void setInkjetPrinter(InkjetPrinter p) { this.inkjetPrinter = p; }
    public void setLaserPrinter(LaserPrinter p) { this.laserPrinter = p; }   // 추가

    public void print() {
        System.out.println("출력을 시작합니다.");
        if (inkjetPrinter != null) {
            inkjetPrinter.warmUp();
            inkjetPrinter.printPage();
            inkjetPrinter.coolDown();
        } else if (laserPrinter != null) {   // 분기 추가
            laserPrinter.warmUp();
            laserPrinter.printPage();
            laserPrinter.coolDown();
        }
    }
}
```
프린터 종류가 늘어날 때마다 `PrintService`에 필드가 늘고, `if-else` 분기가 계속 늘어난다. 나중에 포토 프린터, 3D 프린터까지 추가된다면 `PrintService`는 손댈 때마다 점점 더 복잡해질 것이다. 문제의 핵심은, `PrintService`가 **구체적인 프린터 클래스 하나하나에 직접 의존**하고 있다는 점이다.

## 4. 역할과 구현을 분리하기
이번에는 "출력 장치"라는 역할을 인터페이스로 뽑아내고, `PrintService`가 그 역할에만 의존하도록 바꿔보자.
```java
public interface Printer {
    void warmUp();
    void printPage();
    void coolDown();
}

public class InkjetPrinter implements Printer {
    @Override
    public void warmUp() { System.out.println("InkjetPrinter.warmUp"); }
    @Override
    public void printPage() { System.out.println("InkjetPrinter.printPage"); }
    @Override
    public void coolDown() { System.out.println("InkjetPrinter.coolDown"); }
}

public class LaserPrinter implements Printer {
    @Override
    public void warmUp() { System.out.println("LaserPrinter.warmUp"); }
    @Override
    public void printPage() { System.out.println("LaserPrinter.printPage"); }
    @Override
    public void coolDown() { System.out.println("LaserPrinter.coolDown"); }
}
```
```java
public class PrintService {
    private Printer printer;   // 구체 클래스가 아니라 인터페이스에 의존

    public void setPrinter(Printer printer) {
        System.out.println("프린터를 설정합니다: " + printer);
        this.printer = printer;
    }

    public void print() {
        System.out.println("출력을 시작합니다.");
        printer.warmUp();
        printer.printPage();
        printer.coolDown();
    }
}
```
```java
public class PrintMain {
    public static void main(String[] args) {
        PrintService service = new PrintService();

        Printer inkjet = new InkjetPrinter();
        service.setPrinter(inkjet);
        service.print();

        Printer laser = new LaserPrinter();   // 런타임에 구현체 교체
        service.setPrinter(laser);
        service.print();
    }
}
```
`PrintService`는 이제 `InkjetPrinter`, `LaserPrinter` 같은 구체 클래스를 전혀 알지 못한다. 오직 `Printer`라는 역할(인터페이스)만 알고 있을 뿐이다. `setPrinter(...)`로 어떤 구현 객체가 들어오든 `print()`는 그대로 동작한다.

**실행 과정**: `service.setPrinter(laser)`를 호출하면 `PrintService`의 `printer` 필드가 새 `LaserPrinter` 인스턴스를 참조하도록 바뀐다. 이후 `service.print()`를 호출하면, `printer` 필드는 선언 타입이 `Printer`이므로 `Printer` 타입에서 메서드를 찾지만, 오버라이딩에 의해 실제 인스턴스인 `LaserPrinter`의 메서드가 실행된다. 이것이 바로 **다형성을 활용한 런타임 교체**다 — 프로그램이 실제로 동작하는 도중에도 구현체를 자유롭게 바꿔 끼울 수 있다는 뜻이다.

## 5. OCP 원칙 - 확장에는 열려있고, 변경에는 닫혀있게
방금 만든 구조는 좋은 객체지향 설계 원칙 중 하나인 **OCP(Open-Closed Principle)**를 잘 따르고 있다.
- **Open for extension (확장에 열려있다)**: 새로운 기능이 필요할 때 기존 코드를 확장할 수 있어야 한다.
- **Closed for modification (변경에는 닫혀있다)**: 기존 코드는 수정하지 않아도 되어야 한다.

포토 프린터를 새로 추가한다고 해보자.
```java
public class PhotoPrinter implements Printer {
    @Override
    public void warmUp() { System.out.println("PhotoPrinter.warmUp"); }
    @Override
    public void printPage() { System.out.println("PhotoPrinter.printPage"); }
    @Override
    public void coolDown() { System.out.println("PhotoPrinter.coolDown"); }
}
```
`PhotoPrinter` 클래스를 새로 추가하기만 하면 되고, **`PrintService`의 코드는 단 한 줄도 건드릴 필요가 없다.** `PrintService`는 `Printer` 인터페이스에만 의존하기 때문에, `Printer`를 구현하는 클래스가 몇 개든 상관없이 그대로 동작한다.

- **확장에 열려있다**는 것은, `Printer`를 구현하기만 하면 새로운 프린터 종류를 자유롭게 추가할 수 있고, `PrintService`도 이를 즉시 사용할 수 있다는 뜻이다.
- **변경에는 닫혀있다**는 것은, 새 프린터를 추가해도 `PrintService`처럼 핵심 로직을 담당하는 코드는 수정할 필요가 없다는 뜻이다. (다만 `new PhotoPrinter()`를 생성해서 `service.setPrinter(...)`에 넘겨주는 `main()` 쪽 코드는 당연히 바뀐다 — 프로그램을 조립하고 실행을 시작하는 부분까지 완전히 변경이 없을 수는 없다.)

> **참고**: 이렇게 인터페이스로 역할을 정의하고, 그 역할의 구체적인 구현체를 클라이언트 코드의 변경 없이 자유롭게 교체하는 설계를 **전략 패턴(Strategy Pattern)**이라 부른다. 자바의 여러 표준 라이브러리와 스프링 프레임워크의 핵심 동작 원리도 이 전략 패턴, 즉 다형성을 기반으로 한다.

## 6. 실습 문제
**문제 1. 여러 센서 값을 한 번에 읽기**
`Sensor` 인터페이스를 만들고 `readValue()` 메서드를 선언하자. `IndoorSensor`, `OutdoorSensor` 두 구현체를 만들어 각각 다른 메시지를 출력하게 하자. `Sensor[]` 배열에 두 센서를 담고, `for-each`문으로 순회하며 `readValue()`를 호출하는 `main()`을 작성해보자. (다형성을 활용하면 배열에 어떤 센서가 몇 개 들어있든 같은 반복문으로 처리할 수 있다.)

<details>
<summary>정답 예시</summary>

```java
public interface Sensor {
    void readValue();
}

public class IndoorSensor implements Sensor {
    @Override
    public void readValue() {
        System.out.println("실내 온도를 측정합니다.");
    }
}

public class OutdoorSensor implements Sensor {
    @Override
    public void readValue() {
        System.out.println("실외 온도를 측정합니다.");
    }
}

public class SensorMain {
    public static void main(String[] args) {
        Sensor[] sensors = {new IndoorSensor(), new OutdoorSensor()};
        for (Sensor sensor : sensors) {
            sensor.readValue();
        }
    }
}
```

**문제 2. OCP를 지키며 검증기 추가하기**
놀이공원 입장 티켓을 검증하는 시스템을 만들고 있다. 현재는 `if-else`로 검증 종류를 분기하고 있는데, 앞으로 검증 방식이 계속 늘어날 예정이다. `TicketValidator` 인터페이스와 `validate(int age)` 메서드를 정의하고, `StandardValidator`(나이 제한 없음), `SeniorValidator`(65세 이상만 통과)를 구현해보자. 그리고 검증 방식 이름(문자열)을 받아 알맞은 `TicketValidator` 구현체를 반환하는 정적 메서드를 만들어, 검증 로직을 처리하는 서비스 클래스는 구체 클래스를 전혀 몰라도 되게 만들어보자.

<details>
<summary>정답 예시</summary>

```java
public interface TicketValidator {
    boolean validate(int age);
}

public class StandardValidator implements TicketValidator {
    @Override
    public boolean validate(int age) {
        System.out.println("일반 검증을 진행합니다.");
        return true;
    }
}

public class SeniorValidator implements TicketValidator {
    @Override
    public boolean validate(int age) {
        System.out.println("경로 우대 검증을 진행합니다.");
        return age >= 65;
    }
}

public abstract class ValidatorStore {
    public static TicketValidator findValidator(String type) {
        if (type.equals("senior")) {
            return new SeniorValidator();
        } else {
            return new StandardValidator();
        }
    }
}

public class TicketService {
    public void checkTicket(String type, int age) {
        TicketValidator validator = ValidatorStore.findValidator(type);
        boolean result = validator.validate(age);
        System.out.println(result ? "입장 가능합니다." : "입장 불가합니다.");
    }
}
```
`TicketService`는 `StandardValidator`, `SeniorValidator`라는 구체 클래스를 전혀 참조하지 않는다. 새로운 검증 방식(예: 장애인 할인 검증)을 추가하려면 `ValidatorStore`에 분기 하나와 새 클래스만 추가하면 되고, `TicketService`는 그대로 유지된다.

</details>

## 7. 앞으로의 학습 방향
자바 문법과 객체지향의 핵심 개념(추상화, 캡슐화, 상속, 다형성)을 여기까지 훑었다면, 객체지향이라는 산의 가장 가파른 구간은 넘은 셈이다. 처음에 완전히 이해되지 않아도 괜찮다. 실제로 많은 학습자가 코드를 여러 번 다시 작성해보고 복습하는 과정에서 서서히 감을 잡는다. 다형성이 손에 익을 때까지 이번 강의와 8~9강의 예제들을 직접 변형해서 다시 만들어보는 것을 추천한다.

일반적으로 자바를 실무 수준까지 익히는 흐름은 대략 다음과 같다.
- 지금까지처럼 변수, 타입, 조건문, 반복문, 클래스, 객체지향 같은 기본기를 다진다.
- 예외 처리(try-catch), 컬렉션 프레임워크(List, Map, Set 등) 같은 자바의 실전 도구들을 익힌다.
- 이후 스프링 같은 프레임워크로 넘어가 실제 백엔드 애플리케이션을 만드는 생태계를 학습한다. 스프링은 결국 오늘 배운 다형성과 인터페이스 기반 설계를 극한까지 활용하는 도구이기 때문에, 여기서 다진 개념이 그대로 이어진다.

당장 취업이나 실무 프로젝트가 급하다면, 다음 단계로 곧장 넘어가기 전에 최소한 예외 처리와 컬렉션 정도는 먼저 익히고 가는 것이 좋다. 데이터베이스 관련 지식은 실무 프레임워크를 배우는 과정에서 필요할 때마다 그때그때 채워 넣어도 충분하다.

## 확인 문제 (전체 복습)
1. 부모 타입 변수로 자식 인스턴스를 다루면서, 실제로는 각 자식의 오버라이딩된 동작이 실행되게 하는 성질을 무엇이라 하는가?
2. 추상 클래스와 인터페이스의 가장 큰 차이 중 하나로, 클래스 상속과 달리 인터페이스만 가능한 것은?
3. 새로운 기능을 추가할 때 기존 코드를 수정하지 않아도 되도록 설계하는 원칙의 이름은?

<details>
<summary>정답 확인</summary>

1. 다형성(Polymorphism).
2. 다중 구현(하나의 클래스가 여러 인터페이스를 동시에 구현하는 것).
3. OCP(Open-Closed Principle).

</details>

## 핵심 정리
| 개념 | 설명 |
|---|---|
| 역할과 구현 | 역할(인터페이스)을 사용하는 쪽은 구현(클래스)의 세부 사항을 몰라도 됨 |
| 런타임 교체 | 다형성을 이용하면 프로그램 실행 도중에도 구현 객체를 자유롭게 바꿀 수 있음 |
| OCP 원칙 | 확장에는 열려있고, 변경에는 닫혀있어야 좋은 설계 |
| 전략 패턴 | 인터페이스로 역할을 정의하고, 구현체를 클라이언트 변경 없이 교체하는 설계 패턴 |
| 다음 학습 순서 | 예외 처리 → 컬렉션 프레임워크 → 스프링 등 프레임워크 생태계 |

10강까지 자바 기본 문법 시리즈가 모두 끝났다. 여기서 다진 클래스, 생성자, 패키지, 접근 제어자, 메모리 구조, 상속, 다형성, 추상 클래스, 인터페이스는 이후 어떤 자바 프레임워크를 배우든 계속 사용하게 될 기초 체력이다.
