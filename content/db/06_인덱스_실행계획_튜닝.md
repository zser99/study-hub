# 쿼리가 갑자기 느려졌을 때 가장 먼저 볼 것 — 인덱스와 실행계획

로컬에서는 잘만 돌던 쿼리가 운영 DB에 데이터가 쌓이자 갑자기 몇 초씩 걸리기 시작한다. 이런 상황에서 "인덱스를 걸어보자"는 말은 쉽게 나오지만, 정작 왜 느린지 눈으로 확인하지 않고 인덱스부터 거는 건 위험하다. 오늘은 인덱스의 원리와, 쿼리가 느린 이유를 실제로 확인하는 도구인 실행계획을 다룬다.

## 인덱스: 책의 찾아보기

인덱스가 없으면 DB는 조건에 맞는 행을 찾으려고 테이블 전체를 처음부터 끝까지 훑는다(Full Scan, `Seq Scan`). 인덱스는 책의 찾아보기(색인)처럼 값을 빠르게 찾도록 미리 정렬해둔 구조로, 보통 균형 트리인 B-Tree를 기본으로 쓴다. 데이터가 수백만 건이면 인덱스 유무에 따라 조회 속도가 수백~수천 배 차이 날 수 있다.

다만 공짜는 아니다. 데이터를 추가·수정·삭제할 때마다 인덱스도 같이 갱신돼야 해서 쓰기 성능이 떨어지고, 저장 공간도 더 든다. 그래서 원칙은 이렇다: `WHERE`, `JOIN`, `ORDER BY`에 자주 등장하는 컬럼, 그중에서도 값의 종류가 다양한(선택도가 높은) 컬럼에 우선 인덱스를 걸고, 안 쓰이는 인덱스는 주기적으로 점검해서 제거하자.

```sql
-- 자주 쓰는 조회 조건에 인덱스
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date DESC);

-- 특정 값만 골라 색인하는 부분 인덱스 (테이블의 5%만 대상이라면 크기↓ 속도↑)
CREATE INDEX idx_orders_pending ON orders (created_at) WHERE status = 'PENDING';
```

## 실행계획: 쿼리가 느린 이유를 눈으로 보기

`EXPLAIN`은 예상 실행계획만 보여주고, `EXPLAIN ANALYZE`는 실제로 실행해서 측정값까지 보여준다. 쿼리가 갑자기 느려졌거나 분명 인덱스를 만들었는데 안 쓰이는 것 같을 때 가장 먼저 열어봐야 하는 도구다.

```sql
EXPLAIN ANALYZE
SELECT s.name, c.title FROM students s
JOIN enrollments e ON e.student_id = s.id
JOIN courses c ON c.id = e.course_id
WHERE s.major_id = 1;
```

결과를 읽을 때 확인할 포인트는 세 가지다.

- **스캔 방식**: `Seq Scan`이 보이면 인덱스가 필요하다는 신호다. `Index Only Scan`이 보이면 테이블에 접근하지 않고 인덱스만으로 답을 낸 것이라 가장 빠르다.
- **예측 행 수 vs 실제 행 수**: `rows`(예측)와 `actual rows`(실제)가 크게 차이 나면 통계 정보가 오래됐다는 신호다. `ANALYZE 테이블명`으로 통계를 갱신하자.
- **버퍼**: `shared hit`(메모리에서 읽음)과 `read`(디스크에서 읽음)의 비율로 캐시 히트율을 가늠할 수 있다.

## 자주 하는 실수, 안티패턴 체크리스트

느린 쿼리에는 공통적인 패턴이 있다. 하나씩 점검해보자.

| 안티패턴 | 문제 | 해결책 |
|---|---|---|
| `SELECT *` | 불필요한 데이터 전송, 커버링 인덱스 불가 | 필요한 컬럼만 명시 |
| `WHERE YEAR(date)=2026` | 인덱스 컬럼에 함수를 씌워 인덱스 무력화 | `WHERE date >= '2026-01-01' AND date < '2027-01-01'` |
| `WHERE id = '123'` (id가 정수형) | 암묵적 타입 변환으로 인덱스 무력화 | 같은 타입으로 비교 |
| `LIKE '%키워드%'` | 앞 와일드카드 때문에 인덱스 미사용 | 전문 검색 인덱스(GIN + pg_trgm) 활용 |
| 반복문 안에서 쿼리 N번 실행 | N+1 문제로 DB 과부하 | JOIN 또는 `IN` 절로 한 번에 처리 |
| `LIMIT 10 OFFSET 100000` | 뒤 페이지로 갈수록 선형으로 느려짐 | 마지막 위치를 기억하는 커서(Keyset) 방식 |

이 중에서도 N+1 문제는 특히 자주 만난다. 반복문 안에서 학생 한 명씩 조회 쿼리를 날리는 대신, `JOIN` 한 번으로 필요한 데이터를 다 가져오는 습관을 들이면 쿼리 수를 수백~수천 배 줄일 수 있다.

데이터 양이 아주 많아지면 테이블을 날짜나 지역 등 기준으로 나눠 저장하는 파티셔닝도 고려할 수 있다. 조회 조건에 파티션 기준 컬럼이 포함되면 해당 파티션만 읽고 나머지는 건너뛰기 때문에(파티션 프루닝) 대용량 테이블에서 효과가 크다.

**오늘의 한 줄 요약**: 느린 쿼리를 만나면 감으로 인덱스부터 걸지 말고 `EXPLAIN ANALYZE`로 먼저 확인하자. 다음 편에서는 여러 트랜잭션이 동시에 데이터를 건드릴 때 생기는 문제, MVCC와 락·데드락을 다룬다.
